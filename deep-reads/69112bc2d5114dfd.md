节目开头先把主题说得很直接：Codex 这种东西，三个月或六个月前还很糟，但现在已经变成可以作为知识工作入口的工具。主持人 Dan 说，如果你电脑上有一个很好的通用 coding agent，它其实不只适合写代码，也适合任何知识工作。因为如果一个 agent 能自己写软件，它就能用同样方式处理很多需要信息、计划、文件、浏览器和外部工具的工作。

Austin 补充说，自己每天开始工作时，第一个打开的就是 Codex。它会从 Gmail、Slack、Notion、Stripe 和各种数据源里拉取需要的信息。现在他大约 80% 的时间都在 Codex 里工作，因为 app 本身足够快、足够好。Dan 把这描述为一种新的工作操作系统：未来工作在哪里完成、怎样完成，核心界面会越来越像 agent management interface。

这是一次面向 Every 订阅用户的 Codeex Camp，主题是 “Codex for knowledge work”。Dan 和 Every 的增长负责人 Austin 一起演示他们怎样把 Codex desktop app 用作日常知识工作台。

## 从工程师工具变成知识工作界面

Dan 先回顾 Codex 的变化。他说，几个月前 Codex 主要像一个面向资深工程师的 pair programming 工具，而且体验并不好：它会和你争论，让人觉得自己很笨，缺少情绪智能。OpenAI 原本似乎有一种产品分工：vibe coding 发生在 ChatGPT 里，而资深工程师用 Codex 做严肃编程；Codex 被沙箱和各种限制包住，以免做坏事。

但 Anthropic 通过 Claude Code 展示了另一种方向：如果有一个足够快、足够聪明、又有一定情绪智能的模型在你的电脑上，可以访问本地环境，那么这不仅对程序员很好，也会成为知识工作者的入口。程序员开始在 Claude Code 里委托任务，随后各种知识工作也开始被委托给 Claude Code、Claude co-work 等工具。

Dan 认为，OpenAI 看到这种趋势后，对 Codex 做了快速转向。它从一个工程师专用工具，变成了一个他每天使用的工作入口。他用 Codex 做深度工程、写作、招聘等任务。它有文件系统、浏览器、写代码能力，也被包装成 desktop app。现在，模型公司之间正在争夺这种界面：Anthropic 有 Claude Code 和 Claude co-work，OpenAI 有 Codex，xAI 通过收购 Cursor 也进入这个方向，Google 也有 Antigravity，只是还没成为同等日常工具。

Dan 说，这场竞争的本质是，每家公司都在构建自己的 agent management desktop app。它们核心上是 programming agent，但使用场景正在扩展到知识工作。对用户来说，重要的是在不同工具间切换和试用，因为这样才能感受到 agent-first 世界的工作方式。

## Austin 的 agent pill moment

Austin 说，他的 agent pill moment 大约发生在 12 月到 1 月。他花一周时间深入使用 Claude Code CLI，把它接到工作和个人生活中的各种工具。那时他用 Warp 做 CLI 界面，发现 agent 能自动化很多任务，也能作为 thought partner 提升战略思考、数据分析、营销文案等工作。这些任务过去会把人分散到很多 app 和工具里，而 agent 让他感觉这是唯一想要的知识工作方式。

后来 Dan 一直劝他试 Codex。Austin 起初用 Codex 做一个个人 vibe-coded app，觉得它可能更会构建 app，但体验让他很挫败。两个月前的 Codex 会在计划里提出三个工程选项，Austin 看不懂，于是请它解释。它的反应像是在问“为什么不直接照我推荐的做”。他因此继续用 Codex 处理工程类任务，因为结果好，但 80% 的知识工作仍在 Claude Code CLI 里。

直到他们拿到新的 GPT 模型，Austin 感觉对于自己的知识工作，最新 GPT 至少已经和最新 Opus 达到 parity。Opus 在设计等方面仍有优势，但 Codex desktop app 的速度、sub-agents、自动化建议和执行体验，成为真正差异点。Austin 说，自己现在每天登录后先打开 Codex。早上要做这次 camp 的 run of show，他只要告诉 Codex，它就知道从哪里找上下文，把 run of show 做出来，推到 Notion，再发到 Slack。

Dan 认为，这会在一段时间内成为赛马：每隔几周或几个月，一家公司会暂时领先，另一家公司再追上。最终可能形成不同生态，但现在切换成本还比较低，甚至可以让 Codex 帮你抓取 Claude 那边的上下文。

## Every Growth OS：把业务上下文放进一个 Codex 文件夹

Austin 演示自己的 Codex app。他喜欢 Codex 的组织方式：folder 下可以有持久聊天，也可以在同一个 app 里同时处理知识工作和偶尔提交 PR。他有一些个人 vibe-coded app、个人 OpenClaw，以及一个最重要的 “Every Growth OS” 文件夹。

这个文件夹里有 secrets 和 keys，连接 Every 每天用的工具；还有 project instruction files，用来解释 Every 的业务、团队关心什么、怎样协作。文件夹里还放了一些 reviewer agents，灵感来自 Compound Engineering。原版 Compound Engineering 的 review step 面向工程，检查安全、前端设计等；Austin 为知识工作 fork 出一套适合自己的 review：战略是否和公司目标一致、数据是否准确等。

他给编辑 Kate 展示如何入门 Codex 时，用了一个通用 prompt：先手动把 Gmail、Slack、Notion 等工具连接到 Codex，再在这个 Growth OS 文件夹里启动 Compound Engineering brainstorm workflow，让 agent 看看他最常用的工作工具和当前业务状态，提出哪些自动化能帮助他。

Austin 说，当自己试一个新模型或新 app 时，很喜欢让 frontier model 先告诉自己应该怎样使用它。与其自己先想具体场景，不如让它读上下文，提出自动化方案。Codex 返回的方案包括 follow-up radar、活动 command center、招聘 pipeline 等。这些都是知识工作里常见的痛点：信息从多个渠道涌来，跟进、整理和分派都很耗人。

Codex 还能直接把自动化做出来。Austin 说，这些自动化通常不需要太多调整就能日常使用。比如他有一个每天结束时运行的自动化，会整理还没有回复的信息，起草回复，甚至判断某些 Slack 消息只需要点一个 thumbs-up reaction。Austin 把这类 agent 称为“笨 agent”：它们不需要很聪明，只要每次做正确的小动作。相对的，OpenClaw 或 Every 的 Plus One 这类产品更像聪明 agent，是创造性、战略性 partner。

## 最后审核仍然放回外部 app

现场有听众问，Austin 的 review step 是怎样的。Austin 说，他更喜欢在 Codex 里完成 draft 和 setup，但最后审核发生在外部 app。Slack 消息会变成 Slack 里的 draft reply；邮件会变成 Gmail draft；他会打开原 app 做最后检查。这样能让大脑从 agentic space 里切出来，确认这些内容真的可以发给人。

他也用类似方式处理战略计划。Codex 可以把文档推到 Proof doc 或 Notion doc，最后在人类要接触的地方看一遍。也有人直接在 Codex 里看完就说可以发送，但 Austin 保留外部表面作为最后关口。

另一个听众问，怎样避免邮件自动化误处理重要 lead。Austin 建议先让 agent 采访你，而不是你自己先写规则。你可以用语音转文字工具做 brain dump，解释邮件很乱、希望怎样分流、哪些绝不能自动发送，只能 draft；然后让 Codex 搜索邮件、spawn sub-agents，回来给一份 triage plan。人再看计划，确认有没有把潜在收入邮件自动归档。上线后，可以设置提醒，72 小时后让 agent 审计自动化表现，看它归档了什么、有没有遗漏。

Dan 补充说，他们做 Plus One 时也发现，与其给用户一个复杂 settings dashboard 和 onboarding 流程，不如把 Plus One 暴露成 CLI，让 Codex 或 Claude Code 帮用户设置。因为 agent 已经知道用户电脑和历史对话里的很多上下文，可以把这些免费上下文注入 agent setup。

## 用 Codex 生成 go-to-market plan

Austin 展示了自己最喜欢的知识工作用法。Every 准备公开 launch Plus One，团队已经开过很多内部会议，也在 Slack 里讨论过 go-to-market strategy。人类已经做了营销 case、business case、叙事方向等关键思考，但这些内容分散在会议记录、Slack、Notion 和模板里。

Austin 原本计划本周写完整 go-to-market plan，但临时出现了招聘面试、新模型发布等工作，只剩会议间隙。于是他让 Codex 先启动 brainstorm step，把已有资料整合成 Proof doc。过程中他提醒 Codex 去看即将发布的 posts 和 launches，因为 go-to-market plan 必须考虑内容日程。Codex 产出的 plan 让他觉得已经到 80% 到 90% 可用。

Austin 强调，这不是让模型替 Every 想战略。真正有价值的是，模型把团队已经说过、想过、记录过的 go-to-market strategy 整合起来，检查它和 ICP、目标、叙事定位之间是否一致。过去如果没有这种工具，他要么在白天整块时间写，要么晚上加班到很晚。

他还说，这类 plan 不只是给人看的，也是给 humans and agents 看的。团队成员可以读文档，但更重要的是，他们也可以让自己的 Plus One 或 Codex 总结 Austin 的 plan、提取 business case、围绕 pricing model 继续工作。过去他会花很多精力考虑 proposal 在 CEO 眼里长什么样；现在更关心 plan 是否真的好、是否能被 Dan 的 agent 理解。这让他工作更快，也减少了很多只服务于人类视觉呈现的低价值劳动。

Dan 对此非常赞同。他认为应该 normalize sending agent documents around。Every 做 Proof 就是为了方便发送 markdown documents，大家可以一起 review。AI 写作不一定要模仿人的声音。很多时候，他宁愿读你的 agent 写出的版本，只要你愿意为它背书。真正重要的是：你是否思考过，是否同意里面的内容，如果别人问其中某个 bullet，你能不能讲清楚。

Austin 也说，在 Every，如果你提前分享一份 AI 写的文档，会议上会默认你要对它全部负责。如果有人问到一个点，你说自己都不知道文档里有这句话，那就暴露了。为了避免这种问题，他会在项目规则里写明：不要把我没有在其他上下文里说过的内容放进正式文档；建议可以在 chat 里发给我，但不要写进文档。即便如此，他仍然保留最后 review。

## 用 Codex 建 KPI source of truth

Austin 还展示了一个混合知识工作和工程的例子：重建 Every 的 KPI tracker。Every 有很多业务线，数据来自不同来源。传统工具很难把所有指标放进一个对人和 agent 都友好的 source of truth。Austin 正在 Notion 里重建 KPI sheet，让任何人或 agent 都能查看付费订阅试用、新页面浏览量、Monologue iOS MRR 等指标，并和计划对比。

这个表不只是给人看。如果 source of truth 足够可靠，agent 就能根据它采取行动。比如 SEO 某个关键词落后于计划，agent 可以直接去试着 ship 一组 landing pages。前提是 KPI sheet 的数字必须准确。

Austin 起初想让 Codex one-shot 整个表，因为它有 API keys 和上下文。但每次结果都差 5% 到 10%，可能是格式、数字或框架不对。MRR 这样的数字不能差 3% 或 5%，否则公司无法用它运营。因此，他最后强迫自己 column by column 地验证，每一列从头到尾确保准确、可辩护。

他觉得这很奇怪：模型已经强到让他期待它能一次做完，但现实中仍需要人给出指标定义和验证标准。Codex 会用 Notion worker tool、Stripe、社交数据、脚本等他不完全理解的东西，最后生成一个每六小时更新的 Notion database。Austin 不需要工程师时间，也不需要外部顾问，只要理解业务指标应该怎样工作，就能推动这个工具完成。

Dan 补充说，弄清楚自己赚了多少钱、增长了多少，几乎是哲学问题。比如 MRR 并没有唯一客观定义，重要的是选择一种方式，并且每次都用同样方式计算。

## 招聘和 outbound 搜索

Dan 还分享了一个让他震撼的知识工作用法：招聘。Every 在招 L&D 负责人时，他想到 General Assembly 是 2010 年代纽约很擅长技术教育课程的公司。如果要找能做 AI 课程的人，也许那些曾在 General Assembly 做过课程、后来又进入 AI 的人就是好候选。

于是他直接让 Codex 找一份 GA alum 列表，再筛选出后来进入 AI 的人。Codex 给出名单后，他点开第一个人，发现非常合适，而且对方还关注了他 Twitter，于是直接私信。Dan 说，这种“从干草堆里找针”的 outbound effort，过去要花很多时间筛应用、做搜索，现在 agent 可以很快给出高质量起点。

## Compound Knowledge 和工作方式

有听众问，Austin 用的是不是原版 Compound Engineering plugin。Austin 说，原版对知识工作已经很好用，但他后来 fork 出一个公开的 `compound-knowledge`，把 review step 改成更适合战略、数据准确性、风格指南等知识工作场景。做这个 fork 本身也是很好的学习过程。比如做社交媒体营销的人，可以把 review 调成检查风格指南、历史表现和渠道策略。

他还说，每次 Codex 或 Claude Code session 结束后，agent 会问要不要 compound 这次学习，把它保存到团队共享 source of truth；也会问这次 workflow 是否应该变成 skill，以后自动调用。这样经验不会只留在一次对话里。

另一个听众问，团队怎样腾出时间玩这些工具。Austin 承认，自己有时会过度投入到工具和自动化建设里，而不是做当天必须完成的业务任务。Codex 自动化反过来帮他提醒需要交付的事情。但更大的答案是文化：Every 把玩新工具当作工作的一部分。

Dan 说，工具和 workflow 变化太快了。如果只把自己当前工作方式跑到最快，另一个人使用新范式和新工具，可能默认就会超过你。玩工具看起来像浪费时间，其实是在把自己升级到另一个游戏层级。Every 每年两次有 think week，团队停下日常工作，花一周一起探索新东西、构建、学习。不一定每个公司都要做一整周，但每季度拿出一天给团队玩和学习，是很值得的。

最后，Dan 把这次 camp 总结为：Codex 这类 agent management interface 正在改变知识工作。它不只是帮你写一点代码，而是把已经存在于会议、Slack、Notion、邮件和数据库里的思考组织起来，变成可执行、可验证、可交给其他 agent 继续使用的工作产物。
