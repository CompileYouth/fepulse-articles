节目开头先剪出 Ravi 的几个核心判断。他说，很多 AI prototype 让人感觉像 AI slop，原因往往很微妙。常见错误是，人们没有用 360 度的方式去思考 context，只是写一个很快的 prompt 或一份很短的小 spec，就期待原型工具能生成和过去专业流程一样高保真的东西。他还提到 data context：JSON 是定义结构化数据的好方式。如果有一个独立数据文件，就可以直接把 down tempo 换成 psychedelic rock，保存后 prototype 就会使用完全不同的数据集。最后他说，团队工作方式正在从快速流水线变成更像 jazz band。

正式访谈里，主持人介绍 Ravi：他以前是 Tinder 的 CPO，现在是产品顾问，也是全职 vibe coder。主持人认为 Ravi 在 AI prototyping 上做了很多深入思考，所以希望他展示自己的工作流。

## 从 prompt engineering 到 context engineering

访谈先从一个流行说法开始：不要只做 prompt engineering，而要做 context engineering。主持人问这到底是什么意思。Ravi 说，他很喜欢从 prompt engineering 转向 context engineering，因为这个说法更准确地描述了真正要做的事情。

他给出的定义是：context engineering 是设计和构建系统，让 AI model 获得完成任务所需的正确信息和工具。这个变化背后，是从“和模型对话”转向“设计模型完成工作所需要的全部信息”。

Ravi 说，很多人在做 prototype 时，最大的错误就是没有完整地思考 context。过去做产品时，人们会有很多 artifact：需求、设计、数据、已有产品约束等。这些都是产品生命周期里的关键部分。但现在很多人只写一个快速 prompt 或小 spec，就希望原型工具生成和过去同样高保真的东西。Ravi 想展示的是，怎样从 full stack 的角度思考 context，把不同类型的关键信息喂给原型工具或 vibe coding 工具，从而得到更稳、更真实的输出。

主持人说，自己做 prototype 时经常只是放一些截图或一句 prompt，很多原型也是 disposable 的。但 Ravi 的意思是，如果这个设置做得好，尤其是从现有产品继续加功能时，就可以反复使用同一套 prototype。Ravi 回应说，prototype 最后是 disposable 也没关系。关键是，一个好的 prototype 应该是 decision-making tool。做 prototype 之前，要先想清楚它要帮助做什么决策。

如果 prototype 要用于和客户交流，它必须足够像真实产品，让客户产生 suspension of disbelief。否则客户会从“我正在使用这个东西”切换成“如果真的有这个东西我可能会怎么做”。一旦客户开始谈论 would do，研究准确性就会下降。Ravi 希望客户谈论的是正在做什么，而不是理论上会做什么。要达到这种效果，prototype 需要比普通 prompt 更高的 fidelity。

## 用多个工具搭一个自己的 multi-agent 流程

Ravi 接着开始 demo。他说，做 prototype 时，不一定只用一个工具。可以把多个工具组合起来，像是自己 hack 一个 multi-agent system。Claude 可以做一件事，ChatGPT 可以做另一件事，prototyping tool 做第三件事。这样做的好处是，只把原型工具绝对需要的 context 给它，而不是把许多中间步骤都塞进去污染上下文。

他使用的是 Reforge Build，一个面向已有产品团队的原型工具，适合把设计系统、现有产品 context 等整合进 prototype 过程。

他先展示一个典型 prompt。目标是创建一个音乐流媒体 app 的 genre detail page，比如 Spotify 里某个音乐类型的详情页，让用户看到与这个类型相关的 albums，并按时间线理解这个 genre 的演化。

这个 prompt 偏功能描述，像一个 mini spec：为 down tempo 构建一个 music genre detail page；页面要有 hero image、顶部大图、genre header；要显示 genre 名称和重要 artist tags；还要有 albums timeline，按年份列出 milestone albums。每个 album 要有 artwork、名称、album title 和关于其重要性的简短描述。

Ravi 说，这些 context 并不多，但足够让工具理解要构建什么。工具会扩展 prompt、推理用户到底想要什么，进入一个多步骤模式，创建 todo list，然后按 todo list 构建。即使用很少的信息，也能得到不错的输出。生成结果里有 down tempo 音乐类型介绍、关键艺术家，以及按年份组织的 album 列表。这些文案和内容基本来自模型训练数据，模型在做 prototype 的同时，也在帮忙 copywriting。

但这个结果仍有问题。最明显的是没有 album covers。音乐流媒体平台里用户会期待看到专辑封面，以及更多让体验真实的细节。所以它只是一个起点。Ravi 说，如果从不同类型的 context 出发，就能获得更具体的控制，构建更 robust 的东西。

## functional context 之后，要加入 visual context

Ravi 把刚才的 prompt 称为 functional context。下一层重要 context 是 visual context。在产品设计里，wireframe 通常非常关键。

他用建房子类比：如果建筑师只给你一份 memo，说房子有几个房间、多少面积，但不会画蓝图，你绝不会真的开始盖房子。因为无论 memo 多详细，你都无法想象最后成品是什么样。建筑是三维体验，软件是视觉的二维体验，所以也需要蓝图，才能理解 spec 最终会怎样被渲染成体验。

Ravi 在 Figma 里花了大约 20 分钟画了一个 wireframe，定义这个界面应该是什么样。他说，单靠文字，原型工具其实已经很接近 wireframe，但有些地方不够理想，比如 header 不够紧凑，响应式也不好。移动端宽度下，album cover 占了太多空间，description 没有足够位置。而 wireframe 里，他明确设计为 album cover、artist、album name 在一行，description 和 tags 另起一个全宽区域。

他随后只上传 wireframe，再加一个很短的 prompt：用这个 wireframe 为 down tempo 构建 genre detail page，使用 dark theme、圆角按钮和特定颜色。工具对 wireframe 的理解非常好，不是机械复刻图片，而是把它当成 wireframe 解读，再补全细节。结果是一个“活的 wireframe”：内容不多，因为 wireframe 里没有内容，但 UI 和 UX 比第一版更好。

这就展示了两种 context：一种是文本的 functional context，一种是视觉的 visual context。不过到这里仍然不能直接拿给客户看，因为它还是 dummy data。

## data context 让 prototype 变得真实

Ravi 说，下一层要考虑的是 data context，也就是驱动体验的底层数据。他打开 Claude，展示怎样用其他工具为 vibe coding 或 prototyping session 准备上下文。

他给 Claude 的要求是：研究 down tempo 音乐历史，想 prototype 一个按历史浏览音乐的功能，请生成一个 JSON 文件。JSON 是结构化数据格式，任何 prototyping tool 或 vibe coding tool 都能理解，就像今天大家常用 markdown 给工具写 prompt 一样普遍。

这个 JSON 要包含 genre 名称、genre 描述、代表性艺术家列表，以及 15 到 20 张 milestone albums。每个 album 包含名称、发行日期、艺术家、一到两句说明和 tags。Claude 可以用 web search，也可以用训练数据来填充。输出结果是一个结构化文件，里面包含 genre 描述、seminal artists、milestone albums、release date、tags 等数据。

但音乐体验还需要准确的 album covers，只有文字不够真实。Ravi 说，Claude 可以接 MCP servers。他找不到完全符合需求的 album cover MCP server，于是用 Claude Code 自己做了一个，大概花了一小时。这个 server 可以从免费服务拿到 album cover，而不需要 Spotify API 账号。

他让 Claude 使用这个 MCP server，为每张专辑找到对应 cover URL。这样数据集里不仅有文字数据，还有真实图片 URL。随后他把完整 JSON 复制出来，放进一个 data-centric prompt：为 down tempo 构建 genre detail page，使用以下数据。

这一次，他没有告诉工具页面具体长什么样，也没有说要 header 或 year-by-year albums list，只给了数据。原型工具会理解 JSON 结构，并自己判断怎样组织 UX。结果里出现了 follow genre、play essential albums、about section、seminal artists，以及一个 2x2 album grid。用户可以搜索、排序，也可以按 tag 过滤，比如 hip hop 或 cinematic。

主持人说，album cover 的确让差别非常大。Ravi 也说，这是第一个他觉得可以放到用户面前、真正获得用户数据的 prototype。它仍然不是最终版本：用 wireframe 得到的版本 UX 更符合他的明确设计，但数据不真实；用数据得到的版本更真实，有一些 AI 自己想到的好点子，但不完全符合他想测试的设计。

## full stack prompt：功能、视觉、数据一起给

最后一步是把 functional context、visual context 和 data context 合并成 full stack prompt。Ravi 用 markdown 组织 prompt：构建 music genre evolution feature，列出功能需求；要求根据附带 wireframe 设计页面；指定颜色；再要求用下面的数据填充页面。他还补充要求从 URL 数据里拉取 album covers，并把数据保存成独立文件 `data.json`。

这次生成的界面更完整、更真实。它看起来像 Ravi 在 Figma 里快速画出的 wireframe，也包含真实的 album data、album covers 和 tags。Ravi 说，这个 prototype 看起来 polished，不像 AI slop，可以放到用户面前，测试他们是否真的想要这种体验。

这种做法还有一个好处：prototype 更容易迭代。因为工具同时得到了视觉、数据和功能上下文，它生成的代码更模块化。比如要求把 album covers 做大，工具不仅能放大图片，还会继续正确拉取 image data。相比让 AI 自己决定所有细节，这种方式更容易得到结构合理、可修改的 prototype。

主持人说，这听起来很像 waterfall 并没有死，只是被加速了。过去 spec、wireframe、data structure、code 是一个线性过程，现在也仍然需要这些东西，只不过可能变成十分钟的 waterfall。Ravi 提出另一个类比：过去像快速流水线，product、design、engineering 顺序接力；现在更像 jazz band。每个人有自己的乐器和专业，但大家互相 riff，lead 可能随时改变。Product、design、engineering 不会消失，但会以更紧密、更协同的方式工作。

## 数据文件独立后，prototype 可以快速换主题

Ravi 展示了为什么要把数据保存到独立 `data.json`。如果客户对 down tempo 没兴趣，这个 prototype 不一定能获得好反馈。于是他回到 Claude，让它生成 psychedelic rock 的类似历史数据，并通过 album cover MCP server 加上专辑封面。这个过程大概花 15 分钟。

生成新 JSON 后，他只要复制数据，替换原来的 `data.json`，保存，prototype 就变成 psychedelic rock 页面。页面里会出现 psychedelic rock 的描述、关键艺术家，以及 genre 随时间演化的专辑列表。

Ravi 说，用 full stack context 思考，可以生成更真实、更可信的 prototype，同时也能得到结构更好、更灵活的 prototype。因为 data context、visual context、functional context 本来就接近软件系统的结构：前端、底层数据结构和服务。当你用这种多维上下文给 AI，它更能理解 prototype 的底层架构应该怎样组织。

主持人说，自己以前变懒了，只会给 AI 模糊请求。他原以为 Ravi 会把 JSON 直接粘到 AI 聊天窗口里让它更新，没想到独立数据文件更快、更清楚。Ravi 回应说，他尽量保持 chat 里的请求干净，把数据准备交给其他工具，必要时也会直接编辑代码或替换代码。

## 图片、MCP 和原型里的真实感

主持人继续追问图像资产：Ravi 是否通常会通过免费素材、生成图片，或者像这次一样做 MCP server。Ravi 说，他会先检查是否已有 MCP server。比如如果做电影，也许已经有 movie cover MCP server。当时他找不到能满足需求的 album cover server，所以才让 Claude Code 帮他做。

他的 prompt 大致是：给定 album name 和 artist，希望返回一个免费的 URL，不需要 API key。某些服务提供了免费的 album art，于是 Claude Code 就基于这些服务构建了 server。他测试到能用之后，就把它作为本地 MCP server 留在电脑上。它不需要部署到 GitHub 或其他地方，只要编辑本地 Claude settings 就能使用。

他还做过 location 相关的 MCP server，用于旅行原型，比如给 Eiffel Tower 或 Paris 拉取图片。Ravi 认为，Claude、Claude skills 和 MCP servers 组合起来，会形成一套很好的能力调色板，用来创建更真实的数据集。

## prototype 不是 production code 的替代品

主持人提出一个 hot take：他和 Ramp 的 CPO Jeff 聊过，对方说他们的 PM 不做 prototype，而是直接 build 并提交 PR。既然构建已经这么容易，为什么不直接提交真实代码？

Ravi 用 sketch 和 oil painting 类比。如果你已经知道自己想要什么，并准备承担生产代码的复杂性和时间成本，那当然可以直接做 production code。非技术人员也能做到这点很棒。但 prototype 的价值在于灵活：你不必被当前系统结构、当前数据限制住。很多艺术家在完成作品前会做大量草图和 study，用来探索方向。产品和设计也仍然需要这种能力，在承诺一个方向之前，先不受生产细节束缚地探索 solution space。

主持人又问，很多设计师仍然使用 Figma 等工具，但现在用代码探索似乎也很快，可以一句话让工具生成另一个 2x2 grid 版本。设计工具会不会重要性下降？

Ravi 说他不这么认为。文本思考和视觉思考是两种不同方式。回到建筑蓝图的类比，不能没有蓝图就建房子，也不应该没有视觉探索就构建视觉体验。你可以在代码里做视觉探索，也可以用 prototype tool，但如果心里已有特定体验，用纯文本来回调会很慢。相反，你可以画在纸上拍照，用 Balsamiq，用 Figma，或者任何能表达视觉意图的工具。关键是要知道，有时候 visual prompt 是向模型解释你想要什么的最佳方式。

Ravi 强调，不必在文本、视觉、数据之间二选一。可以根据需要组合不同 context。有时候只给数据，AI 自动补出的 UX 会带来有趣 brainstorm；有时候你需要更明确的视觉目标。重要的是把这些方式都放进工具箱里，缩短从想象到 prototype 或 production feature 的路径。

## PRD 还会存在，但顺序会变

最后主持人提到，过去 PM 时代常常写 17 页 PRD。他很高兴那种阶段可能结束了，但 PRD 里仍有 prototype 不能表达的东西，比如为谁构建、解决什么问题、成功目标是什么。这些是否仍然应该存在？

Ravi 说，过去大家习惯线性流程：先 PRD，再 wireframes，再 detailed designs，再 MVP。原因是每个 artifact 都很贵，所以只有前一步证明方向没错，才创建更贵的下一步。现在这些 artifact 的成本下降了，所以不一定再需要线性关系。有时 PRD 在 prototype 前，有时 PRD 在 prototype 后，都可以。

真正重要的是理解自己想回答哪些问题。写 prototype 或 PRD，本质上都是为了回答一组问题。很多团队会先直接进工具，做出 feature，拿给客户看，得到反馈，再确认方向，然后再写 PRD。在那个 PRD 里，不需要重复所有可视细节，而是解释 prototype 无法解释的东西：我们要解决什么问题，成功指标是什么，它怎样连接到长期战略。

Ravi 认为，单个 artifact 不能完全解释自己，但多个 artifact 放在一起，可以形成清晰的前进路径。流程会变得更 organic，步骤会被打乱，这没有问题。关键是：为了确认正确方向、为客户和公司创造价值，我们还需要哪些信息和工具。

主持人也说，过去团队可能按 waterfall 做三个月，最后发布时客户说其实不想要。现在 prototype 便宜又有趣，可以更早给客户看，比文档更 visceral。客户能直接说“我想要”或“我不想要”，更快得到答案。

Ravi 同意。他说这对 execs、stakeholders、团队和客户都好。过去真正 product-centric 的公司，往往敢于做很多最后不会发布的东西，用浪费的工作换方向正确。但这以前是最大、最成功、最赚钱公司才有的特权。现在每家公司都能这样做。一个公司是否 AI native，标志之一可能就是：是否创建了更多最后不会发布的东西，因为它们更早发现哪些方向不对，并更早找到正确方向。
