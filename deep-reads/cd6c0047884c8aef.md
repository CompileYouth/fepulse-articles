这场对谈的嘉宾是 Anthropic 里负责 Claude Code 和 co-work 的产品负责人 Cat Wu。节目一开始，主持人先抛出一句她自己的判断：要做到“恰到好处的 AGI 化”其实很难。做一个面向未来超级强模型的产品愿景并不难，难的是在当前模型能力下，怎样把能力尽量榨出来、做成今天就能让用户用起来的产品。

主持人先问她在团队里的角色，尤其是她和 Boris 的分工。因为外界大多知道 Boris 是 Claude Code 的关键人物，也知道他自己写很多代码、推进很多功能，但很多人未必清楚产品这边到底是怎么配合的。Cat 说，她非常幸运能和 Boris 搭档。Boris 是技术负责人，也是很强的产品愿景型人物，擅长定义产品在三个月、六个月之后应该长成什么样，甚至去想那个“更 AGI 化”的版本是什么样子。而她的工作，更多是在“今天”和“那个未来愿景”之间搭桥：从现在往那边走，路径是什么；哪些跨职能团队要被拉齐；功能准备好时怎样保证没有额外阻碍挡在上线前面。

她说，自己花很多时间在 cross-functional 协调上，让市场、销售、财务、算力容量这些团队都对齐方向，确保功能 ready 的时候不会被组织流程卡住。她也补充，两人的边界实际上非常模糊，大概有 80% 的部分是高度 mind-meld 的，剩下 20% 的事可能是某一方更在意，于是那一方自然主导。

节目接着进入一个外界特别关心的话题：为什么 Anthropic 的发货速度这么快。主持人说，他从来没有见过这么高频的发货节奏，甚至有人专门做了 Anthropic 发布日历，几乎每天都有新东西上线。Cat 先讲了她最近大量面试 PM 的感受。她说，现在很多 PM 都在用一种很旧的方式理解自己的工作，这在 AI 时代会出问题。过去技术变化慢，团队可以按六到十二个月的节奏做规划，因为代码很贵，产品经理的重点是拉齐很多依赖团队，保证功能最终能落地。

但她认为，现在模型能力进展快，工程速度也被 AI 大幅提升，所以很多产品功能的时间尺度，已经从六个月缩到一个月，甚至缩到一周或一天。于是，PM 的重点也跟着变了。过去那种把大量精力放在多季度 roadmap 对齐和跨团队排期上的方式，不再是最重要的。现在更重要的是：怎样把一个想法尽快送到用户手里，怎样在团队里建立一种机制，让工程师或 PM 有了想法之后，本周就能把它做出来并放给用户试。

主持人顺着这个话题追问，那些最适合做 AI native 产品的 PM，到底是什么样的人。Cat 说，她觉得最关键的能力还是 product taste。因为当代码变得更便宜时，更值钱的就不再是“能不能把东西做出来”，而是“到底该做什么、该怎么做、什么值得被写出来”。她还强调迭代速度。对于 AI 原生产品来说，最重要的是不断试，找到某种方法，让团队真的可以每周上线功能，而不是还在旧节奏里慢慢打磨。

主持人问，那为了让团队跑到这么快，PM 具体在做什么。Cat 先说，第一件事是设定清楚目标。因为大模型能力太通用了，这反而会带来巨大模糊性：你到底在给谁做产品，要解决什么问题，最重要的 use case 是什么。如果这些都不说清楚，大家会很容易沿着不同方向乱跑。她举例说，假设他们要解决的是权限提示过多、让专业开发者在企业环境里更安全地接近“零权限弹窗”，那这个定义本身就会排除掉很多无关做法。也就是说，一个好的 PM 要把目标收紧，而不是把可能性越说越大。

第二件事，她说是建立可重复的发货流程。以 Claude Code 为例，他们几乎所有功能都会先以 research preview 的形式上线，而且会明确告诉用户：这是一个很早期的产品形态，只是一个想法，我们正在收反馈，它不保证永远存在。这种做法的好处是，大大降低了“上线一个功能”时背负的承诺成本。团队不需要等一切都极其完美才能出手，而是可以在一两周内直接放出去，再看真实反馈。

第三件事，是帮助团队建立一个框架，让大家知道什么时候该拉 cross-functional 伙伴进来，也知道这些伙伴分别要承担什么。她举了一个例子：工程、市场、文档之间有一套很紧的协作方式。只要工程师觉得一个功能 ready 了，并且内部 dogfood 过了，就把它发到一个固定的 launch room，文档负责人、产品营销、开发者关系的同事会马上接上，最快第二天就能把对外 announcement 做出来。她说，这种流程之所以重要，是因为它让工程师发货时的摩擦非常小，而 PM 就应该去搭好这种基础设施。

随后主持人问，在这样的节奏下，PRD 还存在吗？Cat 说，存在，但形式变了。她们一方面每周都做非常严格的 metrics readout，让整个团队都理解业务的关键指标、趋势和驱动因素；另一方面，团队还维护一套很清晰的 team principles，写明谁是核心用户、为什么这些人才是重点用户，以及为了这些用户他们愿意接受什么 trade-off。她说，这样做的目的，是让每个人都理解这个业务怎么运转，明白什么是重要的，什么是可以牺牲的，这样很多决策就不需要层层等 PM 拍板。

她也补充说，对某些特别模糊的功能，PRD 还是会写，只不过通常是一页纸左右，写清目标、最理想的 use case、以及当前必须解决的 failure mode。如果是那种确实会牵涉很多基础设施、开发周期可能要几个月的大项目，还是会有更正式的 PRD。也就是说，PRD 没消失，只是不再是所有事情默认的起点。

主持人接着问了一个很多人关心的猜测：Anthropic 现在是不是因为内部已经在大规模使用 Mythos 这样的强模型，才让团队速度变得这么夸张。Cat 的回答是，团队过去几个季度本来就已经很快了，所以不能把原因都归到 Mythos。她承认内部确实会用模型，这当然会进一步提升一部分速度，但更大的原因还是流程和团队期待。Anthropic 的目标是移除一切阻碍发货的东西，让每个人都感觉自己能把一个点子在一周内、甚至一天内送到世界上。

之后主持人又问到一些更具体的事件。比如 Claude Code 源码意外泄露那次，外界反应很大。Cat 说，他们第一时间就调查了，最后确认那是一次人为错误：有人在借助 Claude 写 PR 来更新发布流程时出了问题，而且这个 PR 甚至还经历了两层人工 review。她强调，这是一个流程失败，而不是某个人的问题。最重要的是从中学习，并加更多 safeguard，避免再发生。主持人还追问那位同事还在不在。Cat 说，在，这不是要甩锅给个人，而是流程要改。

另一个敏感问题是 OpenClaw。主持人说，最近很多人不理解为什么 Anthropic 不再允许大家继续拿 Claude 订阅去支撑第三方的 OpenClaw 类产品，甚至觉得这是在伤害开源社区。Cat 的解释是，他们一直看到很大的 Claude 需求，也花了很多精力扩大基础设施、提升 harness 的 token 效率，让用户在订阅下拿到更多价值。但 Claude 订阅最初就不是为第三方产品的调用模式设计的。团队花了很多时间思考怎样给出尽量平滑的过渡，比如在订阅之外给一定 credits，但最后还是不得不做这个艰难决定：优先第一方产品和 API 的使用场景。

访谈后半段又回到 PM 团队本身。Cat 说，Anthropic 目前大概有三四十位 PM，分成几个不同方向。研究 PM 团队负责收集模型层面的客户反馈，并把这些反馈整理给研究团队，同时参与模型发布；Claude Developer Platform 团队负责 API 和开发者平台，包括托管 agent 之类的新能力；Claude Code 团队则直接做 Claude Code 和 co-work；Enterprise 团队负责让这些产品更容易被大企业采用，比如成本控制、RBAC、安全控制；还有一个 growth 团队，横向服务整个产品线的增长。

主持人接着抛出“AI 时代到底还需不需要 PM”这个老问题。他提到另一位嘉宾的观点：因为工程师现在动得太快了，PM 和设计反而更容易跟不上，所以可能不是需要更少 PM，而是需要更多。Cat 的回答很有意思。她说，她觉得所有角色都在重叠。PM 在做一部分工程工作，工程师也在做 PM 的事，设计师也会 PM 甚至写一点代码。你可以通过招聘更多有产品 taste 的工程师来加快发货，也可以保持工程师人数不变，去配更多 PM 来帮助他们做出判断。在她们自己的团队里，更倾向于招聘有很强产品味觉的工程师，因为这样可以降低每次发货的额外 overhead。很多工程师已经可以从在 Twitter 上看到用户反馈开始，一路做到本周内把功能真正上线，中间几乎不需要产品团队介入。

主持人最后问，那对今天的人来说，最值得投资的底层能力到底是什么：工程、设计还是纯产品。Cat 还是把答案落回了 product taste。她说，代码越便宜，决定“该写什么”就越值钱。什么才是对的 UX，什么才是最令人愉快的实现方式，什么是最重要的任务，什么应该先被做好，这些判断会越来越稀缺。因此，不管你是从工程、设计还是产品出发，最后真正拉开差距的，还是这种判断力。
