这期访谈的主角是 Barbara Liskov。主持人在开场先介绍，她是图灵奖得主，以对编程语言和分布式系统的基础性贡献著称。随后，访谈把话题拉到她的职业生涯，以及她当年面对的那些核心工程问题上。

主持人先提到她年轻时申请研究生院的经历。Liskov 说，她本科读的是数学，毕业后申请了几所数学方向的研究生项目，其中包括 Princeton。她收到 Princeton 回信时，上面直接写着“不招收女性”。她说，这件事让她很意外。她知道 Princeton 当时本科不招女生，但没想到研究生阶段也是一样。不过现实就是如此。最后她去了 Berkeley，因为那是她本科所在的学校，也录取了她。但她当时觉得自己还没有准备好继续读数学博士，于是决定先找工作，看看外面的世界是什么样。她拿到的最好一份工作恰好是程序员职位，她说，自己就是这样“阴差阳错”进入了计算机科学。

主持人接着说，她在 Berkeley 一直是非常优秀的学生，所以听到她连一些机会都拿不到，还是会觉得很奇怪。Liskov 回应说，那就是当年的现实。她在 Berkeley 的环境和 Princeton 很不一样。Berkeley 是男女同校，学校里有很多女学生，只是主修数学的女生不多，所以在数学课上女生人数很少，但那种“门直接对你关上、你就是不能做这件事”的氛围，在 Berkeley 并不存在。她也顺便提到，如今顶尖学校里学计算机科学的女性比例已经接近一半，时代已经变了。

接下来主持人把话题转向 20 世纪 70 年代的软件危机，想让她解释当时到底出了什么问题。Liskov 说，那在当时是个巨大问题，因为人们根本不知道怎么构建能够正常工作的“大程序”。那时候你常常会在报纸上看到新闻：某家公司花了几百万美元、投入了几百个人年的工作，去开发一个大型软件系统，最后却只能把它整个扔掉，因为它根本不能工作。她说，问题的关键在于，要让一个大程序能工作，你必须有模块化。你必须把程序拆成小块。每一块都要通过接口向外提供服务，而且这个接口要尽量完整地描述它能做什么。至于模块内部的实现，应该被隐藏起来，外部的人不需要关注它。只有系统按这种方式组织起来，你才可能一块一块地推理它的正确性。

她说，当年大家并不是不知道“模块化很重要”，而是根本不知道怎样设计出真正模块化的系统。当时编程语言里唯一现成的模块化机制其实只是“过程”或者“函数”，但过程并不匹配人们真正需要的模块。她举例说，文件系统、数据库，甚至像 Amazon 这样的复杂系统，都不是“输入一个东西，输出一个东西”的简单过程，而是更复杂的实体。因此，当时根本没有一种模块概念，能和人们想构建的对象真正对应起来。

主持人问，那在这种背景下，最早人们给出的解决方案是什么。Liskov 说，大家会谈模块化，也会写论文强调模块化的重要性，但他们并不知道“模块到底是什么”。于是模块常常被理解成“一块代码”。甚至还有论文在讨论一个模块该有多大。她说，这种思路不会真正解决问题，因为系统是要被设计出来的，你需要一种能指导设计的方法，而不是只把代码机械地分块。她还补充说，当时人们也不清楚模块化的规则到底是什么。

她随后回忆自己在 MITRE 的早期工作。那时候她已经在一个小团队里摸索出一种比当时主流说法更完整的模块化观念。原因很现实：她带着一个不大的程序员团队在做一个复杂系统，她只是想让大家别把事情搞砸。正因为手里已经有这套经验，等她真正开始研究这个主题时，她一下就看到了“数据抽象”这个想法。她说，自己原来脑子里那套模块化机制，本质上就是一组通过若干操作暴露给外界的代码，外界可以从这些操作进入模块，但模块内部所有实现细节、包括内部使用的数据，都不允许外界直接碰。某一刻她突然意识到，这其实就可以被理解成一种数据抽象：它可以表示集合，可以表示序列，也可以表示很多其他抽象对象。于是，新的模块类型就被看清了。

她回头再看当时的一些论文时，会觉得那个想法其实已经“几乎在那里了”，只是还没有人真正把它挑出来。她说，科学里经常会出现这种情况：一个想法在某个时刻已经成熟，而她碰巧看到了它。

主持人接着问，她如何把这些想法带进自己设计的 Clue 语言，以及它后来怎样影响了行业。Liskov 说，第一件事是她和 MIT 的研究生 Steve Zilles 合写了一篇关于数据抽象的论文。那篇论文勾勒了抽象数据类型的概念，以及编程语言该如何支持它。她说，那篇论文影响非常大，首先在研究圈里引起了很大反响。之后 Clue 的工作继续推进，也带动了编程语言领域一系列额外研究。

她接着解释，研究社区当然会关注这些新想法，但公司里真正要写程序的人，需要的是一门有公司支持、能真正用起来的语言。她自己并不想把 Clue 商业化，因为那意味着要进入公司环境，而她对研究更感兴趣。况且那个年代也不是把软件发到互联网，大家就会自然去用的时代，互联网甚至都还不存在。因此 Clue 虽然有一批使用者，但很难成为当时公司会正式采用的产品。后来，美国政府发起了寻找新编程语言的计划，这最终促成了 Ada 的诞生。Liskov 说，这本身就已经说明数据抽象的影响力很大，因为它成了一门正式语言设计时必须考虑的能力。再后来，90 年代 Java 出现，相关理念也进一步进入主流。

主持人接着提起她曾说过“Python 有点问题”，想听听她具体是什么意思。Liskov 说，Python 有模块，但没有真正的封装。也就是说，模块外部的代码还能跑进去“搅和”模块内部在做什么。而封装恰恰是让模块化生效的关键。尤其是在构建大型程序、多人协作时，团队最终往往只和最弱的程序员一样强，因此如果编译器能强制某些坏行为根本不可能发生，那会非常有帮助。她也补充说，Python 的设计目标本来就不一样，它在帮助经验没那么多的程序员快速学会写程序这件事上很有效。至于如何让语言更安全，这一直是编程语言研究者关心的问题，只是她后来已经不再是这个方向的一线专家了。

随后主持人问她是怎么进入分布式计算的。Liskov 说，她读到 Bob Kahn 的一篇文章。Bob Kahn 和 Vint Cerf 一般被认为是互联网的奠基者。Bob 在文中描绘了分布式计算的愿景：一个程序可以由网络上不同计算机上的不同部分组成，但当时没有人真正知道该如何构建这样的程序。Liskov 觉得这是个很好的问题，而她当时也正想找一个新方向，于是就跳进了分布式计算。

她说，最开始她做的其实是一门用于编写分布式程序的编程语言，叫做 Argus。它深受 Clue 的影响，是一种面向对象语言，其中有一种特殊对象叫 guardian。一个 guardian 对应网络中某一台计算机上的一个模块，guardian 之间通过远程过程调用通信。她解释说，分布式计算很快就会碰到一个问题：如果一个计算从某个 guardian 开始，后来又调用了网络上其他节点的 guardian，你最后希望这个计算要么完整地成功，要么完全不生效。为了解决这个问题，她借用了数据库领域里的事务概念，所以 Argus 会把这些计算当作原子事务来运行。

主持人顺势问，这是不是就像跨节点的分布式事务。Liskov 说，是的，这也很自然地把她带进了 viewstamp replication 的工作。她说，那个问题其实已经很像后来的云存储：不管底层具体是文件系统还是什么，你都需要考虑如何把数据存放在互联网上多个地点，只要有足够的节点活着、网络还通，系统就既能保持正确行为，又能始终可访问。

主持人问 viewstamp 到底是什么意思。她解释说，这只是和实现细节有关的一种命名方式，用来判断节点失效、需要其他节点接管时，哪些节点持有最新状态，从而保证接手时不会丢掉之前已经发生的东西。主持人追问，如果时钟不同步怎么办。她说这里根本不依赖物理时钟，只是依赖编号，比如现在是第 25 个 view，下一个就是 26。

当主持人说这听起来很像 Leslie Lamport 的工作时，Liskov 直接回答：是的。她说，自己和 Leslie 实际上是独立地发展出了本质相同的想法。Lamport 的系统后来被叫做 Paxos，而她这边叫 viewstamp replication。主持人问两者到底有何不同。Liskov 说，会有一些技术细节层面的差别，但本质是同一类系统。她还提到，自己知道这类思想第一次真正进入实际系统，大概是在 Google File System 时代。有位曾经的学生在 Google 看到相关设计后，说那其实就是 viewstamp replication。Google 内部的人当时更习惯叫它 Paxos，但在她看来，两者本来就是同一件事。

接着访谈又回到编程语言史。Liskov 说，在她做 Clue 的同时，Alan Kay 在西海岸发展 Smalltalk，Carnegie Mellon 的 Bill Wulf 和 Mary Shaw 则在做另一门数据抽象语言 Alphard。那个年代虽然已经有 ARPANET，但并没有真正意义上的互联网，所以这些研究流派彼此交流很少。她说，自己当时并没有太关注 Smalltalk，而西海岸那边大概也没有太关注数据抽象，这就形成了两条平行发展的研究线。

正是在阅读这些面向对象文献的过程中，她后来发展出了被称为 Liskov substitution principle 的东西。她回忆说，1986 年左右，她受邀去 OOPSLA 做 keynote，于是决定认真读一遍 Smalltalk 以及其他相关语言的论文。她发现 Smalltalk 里有类和子类、继承这些概念，而 Clue 并没有继承，只有相互独立的 cluster。与此同时，她也看到那边的人在讨论所谓的 type hierarchy，想说明父类和子类实现的类型之间到底是什么关系，但一直说不清。

她说，自己一向是从“规格”和“意义”去理解模块的。这和她在 MIT 和 John Guttag 一起开的课程有关。那门课不只教学生模块化和数据类型，也教他们怎么写规格、怎么推理正确性，强调先理解一个东西“意味着什么”，而不是先盯着实现细节不放。所以当她读到那些主要围绕实现去谈类与子类关系的论文时，她会觉得那种思考方式和自己完全不同。她是从行为出发来看这个问题的，于是她得出一个很自然的结论：如果某个地方原本期待的是父类类型，那你用子类替代进去时，它在行为上就必须仍然像那个父类。这后来就成了大家说的 Liskov substitution principle。再往后，她和 Jeannette Wing 还专门写了 behavioral subtyping 的论文，把这件事形式化定义下来。

主持人问，这个名字是怎么来的。Liskov 说，她自己当然没有站在台上宣布“这就是 Liskov substitution principle”。她真正意识到有这个名字，还是 90 年代互联网已经普及之后，有人发邮件来问她：“这样理解 Liskov substitution principle 对不对？”她那时才知道这个说法已经流传开了。她还说，在那之前，她甚至没有完全意识到这个想法后来会被看得这么重要，因为她当时已经在做别的事情了。

主持人又问，为什么有些想法会更“留下来”，比如 Paxos 就明显比 viewstamp replication 更出名。Liskov 笑着引用 Leslie 的说法：“他四处去做报告，而我是在做实现。”她说，Leslie 确实做了很多演讲、写了很多论文，因此更有名气。主持人还调侃说，Paxos 这个名字也更好记。Liskov 也承认，这是个挺可爱的名字。

她随后补充了一点更技术史的背景：无论是 viewstamp replication 还是 Paxos，之所以都能迈出那一步，一个重要背景是她之前做事务系统的经验。在事务里本来就有 leader，leader 会决定是否提交，并问其他参与者能不能提交。难点在于，一旦 leader 自己挂掉了怎么办。viewstamp replication 和 Paxos 真正往前推进的一步，就是能在 leader 失效时切换到新的 leader。

最后她提到，之后又出现了 Byzantine fault tolerance 的工作，那是在更进一步考虑网络中不只是崩溃，还有恶意节点、被攻破节点、错误消息等问题。她说，viewstamp replication 是她和学生 Brian Oki 在其博士论文里做出来的，而后来的 Byzantine fault tolerance 则是她和学生 Miguel Castro 完成的，也是一篇博士论文。Miguel 对这个问题感兴趣，是因为当时 DARPA 发起了相关征题，请大家研究互联网环境下存在恶意攻击时，系统该怎么办。

整场访谈听下来，Barbara Liskov 谈的并不是几个彼此分散的成果。无论是模块化、数据抽象、封装、Clue、Argus、viewstamp replication 还是 Liskov substitution principle，她真正一直在回答的，都是同一个问题：当系统越来越复杂、参与的人越来越多时，怎样把复杂度关住，让系统仍然能被理解、被替换、被继续构建下去。
