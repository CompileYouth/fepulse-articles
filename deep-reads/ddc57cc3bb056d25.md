这期节目一开始，主持人 Dan 先把一个近来在 Every 内部很流行的比喻抛出来：人类是三明治上下两片面包，AI 是夹在中间的馅。主持人说，这个说法最早是 Trevin 提出来的，大家后来把它叫成 “AI sandwich”。节目想讨论的，就是在今天大量使用 agent 和大模型的工作流里，人到底该站在什么位置。

嘉宾 Kieran 先介绍了自己现在在做的事。他是 Cora 的 GM，也参与做了 Compound Engineering。主持人说，Compound Engineering 已经变成 Every 内部很重要的一套工程方法论和插件，很多认真用 coding agent 的人至少都知道它。Kieran 解释说，Compound Engineering 最初是围绕工程工作发展出来的，但他们很快发现，它其实也适用于产品、设计和更广义的知识工作。

他回忆说，最早做 Cora 时，他就一直在想：有了 AI，怎样才能更快地做出更好的工作？最初那版 Compound Engineering，大致分成四个步骤。第一步是 planning，也就是先把计划想清楚，让系统明确知道接下来要构建什么。第二步是 do work，由 agent 去执行、写代码、做设计或者完成其他具体劳动。第三步是 review，因为无论最后出来的是“slop”还是好结果，总得有人检查它到底好不好。第四步也是他认为最重要的一步，叫 compound。也就是在 review 或 planning 过程中，如果发现了值得反复复用的经验，比如某类错误、某种判断、某种模式，那就把这些知识回写进仓库，让 agent 下次在 planning、执行和 review 时都能看见这些过去学到的东西。

他说，这种“把知识沉淀回系统”的能力，是这个插件里最强的一点。因为一旦经验能持续沉淀，agent 就不会每次都从零开始重复犯同样的错。

不过，随着他们把这套方法不断用下去，也逐渐意识到，工作流程里有些部分其实已经差不多“被解决了”。Kieran 说，像 work 这一步，只要前面的 plan 足够好，模型执行计划、做深度工作、持续工作几个小时甚至几天，这件事现在已经越来越可靠。他不是说这里完全不需要一个阶段，而是说自己已经越来越不需要“天天盯着它怎么做”，因为只要计划好，它通常就能做出来。

Review 也在逐渐接近这个状态，planning 也在变强。于是一个更大的问题就浮现出来了：如果这些步骤都越来越能自动化，那人到底还要做什么？难道人真的把自己自动化掉了吗？

Kieran 说，他们后来有一个重要补充，来自 Trevin。Trevin 认为，在 planning 之前还应该再增加两个阶段：brainstorm 和 ideate。Ideate 更像是大范围发散，在一个“很多有趣视角一起在场”的房间里尽量想更多可能性；brainstorm 则更像是面对一个自己还没完全理解的问题时，借助系统和人一起把问题本身想清楚。Kieran 说，他们在这里发现了第一个规律：最前面的这些步骤，尤其是 ideate 和 brainstorm，人必须非常在环。人需要认真思考、提出问题、不断澄清，而模型在这里更像是一个支持者。

但一旦前面的问题想清楚，进入 planning 阶段之后，很多工作就可以比较安心地交给模型。于是他们第一次明确意识到：不是所有环节都一样需要人。真正重要的是知道什么时候人该在环里，什么时候应该交出去。因为只有这样，人才能把脑力留给那些真正值得深思的地方。

Kieran 说，很多 spec-driven development 一类的方法，总是假设人始终都应该在环里，但他不同意这种看法。他认为，精确地区分“人应该插手的地方”和“可以交给模型的地方”，恰恰能让人把精力用在最值钱的位置。

然后他们又在流程的另一端发现了第二个关键点。一个功能、一段代码或一个设计稿即使已经通过自动测试，看起来也都“工作正常”了，但这不等于它已经足够好。Kieran 说，真正让一个东西变得更好的，常常发生在最后：人去点一遍、感受一遍、觉得这里还不顺、那里还可以再美一点，再进一步 polish。这个阶段的价值，不只是验收，更是提升。

他举了 Pomodoro 的例子。传统番茄工作法里，如果你提前十五分钟做完一个任务，剩下的十分钟你不能立刻换任务，而是还得继续待在同一个任务上。Kieran 说，很多时候正是在那段“其实已经做完了，但你还在这个任务里继续看一看”的时间里，真正美的东西才会发生。你会开始继续打磨、继续深入，把东西从“能用”推到“真的很好”。

于是，他们发现第二个需要人强烈在环的时刻，恰恰是在最后。中间可以高度自动化，但最后一个“它到底够不够好、够不够顺、够不够美”的判断，仍然非常依赖人。

讲到这里，主持人把这个结构重新说了一遍：人站在开头和结尾，中间的很多部分由 AI 来完成，所以整个流程像一个三明治，AI 在中间，人是两端的面包。Kieran 说，没错，而且中间那层 AI 可以是任何你想放进三明治里的东西。重要的是，这个模型给了人一个很实际的判断框架：哪些地方应该自己用脑，哪些地方应该主动外包给 LLM。

主持人随后把这个思路推广到更大的问题上。他说，现在大家都在问 AI 和 agent 到底会不会抢走所有工作，而软件工程师看起来像是最早受影响的一批人，像矿井里的金丝雀。但 Every 的内部经验并不是“以后不需要工程师了”。他们还是需要工程师，只是工程师的工作越来越像在管理和引导一个系统，而不是从头到尾亲手完成每一步。

主持人接着提出一个常见反驳：也许现在 brainstorm 和 ideation 还得靠人，但以后 agent 也会越来越擅长这些前面的事情，那到时候怎么办？他自己给出的思考是，不管 agent 再怎么进步，人和模型面对任何问题时，总可以切换问题的框架。比如“我膝盖疼”这个问题，你可以把它局限地理解成“去买 Advil”，也可以继续往上追问，变成“是不是 IT band 太紧”“是不是每天在硬地面上跑太多”。换句话说，同一个问题总能放进更大一层的框架里去理解，而人类特别擅长做这种“换框”的事情。

Kieran 说，他完全认同这一点。归根结底，这都是在为 agent 创造一个能成功的环境，而这件事非常依赖人来“选对问题、选对框架、选对边界”。当然，未来 ideation 本身也会进一步自动化，比如你可以模拟一百个人、几百万人，看他们会怎样思考、怎样反应。但即便如此，如果你真的要把某个作品发布到世界上，想让它算是“你的东西”，那你终究要在某个时刻自己说 yes 或 no。你不能把全部决策权都自动化掉。

他说，这有点像艺术。如果你希望一个作品真正属于你，它就必须以某种方式和你相连。正因为如此，人还需要在那些决定性的时刻亲自参与，也正因为如此，做自己喜欢的事会变得非常重要。因为你最终要对那些结果说“这是我愿意认领的”。

主持人说，他也同意这一点。即使未来可以模拟无数 persona，靠大规模模拟得到一些结论，那也只覆盖了某一类决策。现实里很多关键判断的数据反馈本来就极少，你一个职业生涯里可能也就遇到几次，正因为稀缺，这些判断不容易被大模型彻底吸收掉。相反，那些沉淀在专家身上的 taste、人格、世界观和经验，很难被简单复制。

节目最后，主持人把这整套理解又收束回工作本身。他说，如果要给今天的人一个简单建议，那大概就是：去骑那头野兽，或者说，去做三明治的面包。也就是说，不要假装一切都和以前一样，也不要把所有权全都让给模型。相反，你要主动把自己放在最需要判断、最需要 taste、最需要审美和方向感的地方。

Kieran 最后补充说，这条路对不同人会长得不一样。如果你真的喜欢写代码，那以后也仍然可以写代码，只是你可能会更在意“漂亮的代码”“漂亮的抽象”。如果你更在意界面，那你会把更多精力花在最后的 polish 上。无论怎样，工程师都会变得更像产品人，也更像管理者，因为你要不断决定哪些部分交给模型，哪些地方必须自己上手。最终，最值得做的事，就是去做那些你真正觉得有趣、愿意把它做到很美的工作。
