![](https://i.ytimg.com/vi/oS53by4Hwvo/maxresdefault.jpg)

视频开头，作者说今天要展示怎样从零设计并构建一个移动健身应用。这个应用用来追踪个人训练。以前要做出这样一个漂亮的 app，通常需要工程师、设计师和产品经理组成一个完整产品团队。但他是在白天工作结束之后，晚上花了几个小时把它做出来的。

他先带观众看应用本身。用户可以创建一个新的 workout，比如命名为 Peter's workout，然后往里面添加动作。可以选择 barbell back squat，设置三组、每组八次，也可以添加一组 warm-up set。接着还可以添加 barbell back rows、barbell bench press。保存之后，用户就能点进这个 workout，在训练时实时追踪。

训练过程中，每个动作和每组完成情况都可以通过点击来标记。完成热身动作可以点掉，做完八次也可以点掉。应用里还内置了休息时间。训练完成之后，它会出现在日历里。用户可以点击日期，看到当天做过哪些训练。设置页里还可以在 pounds 和 kilograms 之间切换，也能开关 rest timer。作者说，这已经是一个相当完整的 app。

## 先用 Claude 一起定义需求

作者把整个过程分成三个阶段。第一阶段是和 Claude 一起定义需求。第二阶段是用 Pencil 设计应用界面。Pencil 是一个 AI 设计工具，后面会展示。第三阶段是用 Claude Code 构建应用，并用 Expo Go 在手机上测试。

在需求阶段，他给 Claude 的初始提示是：一起为一个 fitness mobile app 制定需求。他很快定义了三个核心屏幕：新增和编辑 workout 的页面、训练时使用的 workout screen、以及日历页面。

他说自己年轻时用过 StrongLifts 5x5。那是一个类似的训练 app，主要围绕杠铃动作做五组五次。他很喜欢那个 app，但现在年纪大了，不能再一味追求越来越重的重量，因为受伤风险很高。所以他想要更多灵活性，比如三组八次或者其他训练方式。

他特别强调提示里的这一句很重要：这些只是基础需求，要和 Claude 一起继续打磨 spec；Claude 要保持需求清晰，如果有问题，就用编号列表问出来。作者认为，让 Claude 主动提问非常重要，因为需求里很可能会有遗漏的边界情况。Claude 在这里像一个 junior product manager，和人一起把 spec 做出来。

Claude 随后问了很多问题，比如是否需要 progressive overload tracking，是否自动建议增加重量，是否需要组间休息计时器，日历如何交互等等。作者逐一回答。比如 progressive overload 可以先手动记录，除非能用简单方式实现：如果连续三次 workout 都完成了所有组数和次数，就把重量增加五磅。

Claude 继续追问 failed sets logic、pounds 和 kilograms 切换、数据存储等问题。作者又给了一些方向。他说这些回答有些并不精致，就像他会和真实产品同事聊天一样，但正是这种来回迭代让需求变得有趣。

后来 Claude 开始写 markdown 文件，但作者一开始并不想直接要文件，而是想先在聊天里看到需求文本，便于检查。Claude 输出了 app 概览、React Native app 的方向、数据模型、以及各个屏幕的需求。最后还列出一些开放问题。作者又补充：默认三组工作组，目标次数默认八次；对于杠铃，因为他用的是 Olympic barbell，希望自动加入杠铃本身重量，不需要手动输入；主题只做 dark only，并指定主色偏暗红。

他还要求 Claude 明确区分用户可见需求和技术需求，因为下一步要把设计需求交给 Pencil 生成界面。他希望给 AI designer 一些发挥空间，所以在这一步不把设计要求写得过细。于是 Claude 生成了 1.1 版 spec，把设计要求和技术 spec 分开。

## 用 Pencil 生成完整界面

第二阶段是用 Pencil 设计屏幕。作者说这里是“魔法发生的地方”。他把设计需求粘贴到 Pencil 里，里面包含各个屏幕的描述。模型选择 Claude Opus，因为他认为 Claude Opus 和 Gemini 都很适合设计。另一个关键设置是打开 6x，让六个设计 agent 同时工作。

Pencil 随后开始生成界面。作者跳过等待过程，直接展示完成后的设计。这个 fitness app 有主 workout 屏幕，也可以编辑每个 workout、添加 exercises。点击添加动作后，会出现三十多个动作列表。每个动作都可以设置 working sets 和 target reps。训练过程中，可以通过点击圆圈实时追踪完成情况，界面里还有 timer。日历页可以显示整个月做了多少次训练，也能点开某一天看训练详情。还有 exercise history screen，用来查看进步情况，最后还有设置页。

作者说，即使他的电脑不算强，这些设计也在五分钟内生成了，非常惊人。如果想改，可以继续 prompt Pencil，也可以手动改。比如把 bench press 改成别的文字，或者通过类似 Figma 的界面调整颜色。

他还打开了 Pencil 生成的 fitness.pen 文件，展示背后实际发生了什么。这个文件看起来很乱，但本质上是一堆关于字体、来源、padding、颜色、间距等信息的说明。它基本就是一个 JSON 文本文件。作者认为这正是它神奇的地方：所有东西都在文本文件里，而 AI 很擅长读文本文件。

## 把设计和 spec 交给 Claude Code

第三阶段是构建应用。作者回到 Claude 对话里，告诉它自己已经生成了完整设计，包括所有屏幕。他把屏幕信息复制进去，让 Claude 写完整技术 spec。

Claude 生成了技术栈、数据模型、progressive overload 逻辑等内容。作者还特别要求把 spec 拆成三个 milestone，因为他不希望让 AI 一次性把整个 app 全部做完。也许一次性生成也可以，但他的习惯是拆成几个阶段，每一阶段都自己测试和验证。

第一个 milestone 是构建 app skeleton 和完整模板，包括多个基础屏幕。第二个 milestone 是构建 live workout session screen 和 rest timer。第三个 milestone 是添加 calendar 和 exercise history。spec 里还列出了一些 out of scope 的内容。作者强调，还是要认真 review spec，修改它，并继续 prompt AI 改进。比如他觉得 custom exercise creation 应该进入 scope，于是让 Claude 重新改写。

最后，他让 Claude 生成完整的 `spec.md` 文件。这个文件将直接放进 Claude Code。作者说，其实这些也可以在 Claude Code 里完成，但他习惯先用普通 Claude 做需求，因为那时他还不想开始写代码；而 Claude Code 往往会很积极地想直接动手。

他创建了一个 fitness app 文件夹，启动 Claude Code，把 spec 文件放进去。Pencil 有 MCP，所以在 Claude Code 里输入 `/mcp` 可以看到 Pencil MCP 已经连接。因为这个连接存在，他可以问 Claude Code 当前 fitness.pen 里有什么，Claude Code 就能通过 Pencil MCP 获取刚才设计好的所有屏幕。

## 分阶段构建、上手机测试、修依赖问题

作者随后展示昨晚用 Claude Code 构建应用的真实对话。他开玩笑说，因为花了很多时间做这个 app，晚上大概 11 点才睡，结果早上没来得及锻炼，也许他比起健身更喜欢做健身 app。

构建时，第一步是告诉 Claude Code：你已经有 spec、设计和三个 milestone，这些 milestone 是否合理？应该从哪里开始？他希望能够沿途测试。Claude Code 确认 milestone 合理后，他让它开始构建 milestone one。

Claude Code 做的事情包括：从 pen 文件里截图每个设计，运行 Expo app，安装依赖，然后开始搭建各个屏幕。接下来是让应用跑在设备上，也就是跑到他的 iPhone 上。为此需要下载免费的 Expo Go app，也可以用 iPhone mirroring 在电脑上看到手机界面。

这一部分其实迭代了很久。作者说，即使在 AI 编程出现之前，写代码最痛苦的部分之一也是装对库和依赖。他和 Claude Code 来回处理了大约二十分钟，因为 Expo SDK 55 和 Expo Go app 不兼容，后者只支持 SDK 54。所以他们一起把 SDK 降到 54，应用才终于能在 iPhone 上运行。

之后还有一些 UI bug，比如数字键盘挡住屏幕，导致无法编辑组数。他继续来回修这些问题。后面又构建了 milestone two 和 milestone three。最后还做了一轮 polish pass：让 Claude Code 看 fitness.pen UI 文件，检查 spacing 和 UX 哪里不对，再看代码是否干净。作者说，这不是很科学的 prompting，只是他自己在手机上玩应用，看到问题就让 Claude Code 清理。

最后，他创建了一个 GitHub repo，让 Claude Code 把所有东西 commit 进去。整个项目大约有 6400 行代码，覆盖八个屏幕。这样后续如果改坏了，至少可以从 GitHub 回退。

## 下一步是安装到手机或上架 App Store

作者说，这就是完整 app，现在已经能用来做自己的个人训练了。下一步他想把它装到手机上，而不是每次依赖 Expo Go。要上架 App Store，需要支付 99 美元成为 Apple Developer。他直接问 Claude：怎样把这个 app 放到 App Store，或者至少自己测试时不用一直跑 Expo Go？

Claude 给了两个选项：一种是 EAS build，不需要 Xcode；另一种是提交到 App Store。作者认为自己下一步可能会做 EAS build，这样可以把 app 安装到自己手机上，用来做个人训练。如果之后想让它更稳定、更完善，也可以提交到 App Store，甚至也许能从中赚到钱。

最后他回顾整个过程。第一，和 Claude 反复定义需求。关键是让 Claude 主动问问题，然后人来回答，一起补足需求和边界情况。第二，让 Claude 把设计需求和技术需求清楚分开，再把设计需求交给 Pencil 生成屏幕。第三，用 Claude Code 构建应用，并在 Expo Go 里测试。关键是通过 Pencil MCP 让 Claude Code 能访问 Pencil 文件里的设计，并且把实现拆成三个阶段，沿途测试，而不是试图一次性完成所有东西。

作者说，他做这个教程是因为，如果自己能在一整天工作之后，晚上用两个小时做出这个 app，那么其他人也没有理由不去构建自己的东西。现在做东西已经变得非常容易，也非常有趣。每个人都应该成为 builder。不要等别人解释给你听，直接问 Claude 帮忙，然后自己把事情弄明白。
