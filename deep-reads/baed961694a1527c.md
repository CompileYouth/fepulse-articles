节目开始时，主持人介绍 Steve Ruiz 是 tldraw 的设计师、创始人和 CEO。tldraw 被描述为现代 Web 上面向 infinite canvas 的 IDE。主持人先问，tldraw 到底是什么，名字代表什么。

Steve 说，tldraw 其实不代表什么。他买下这个域名时，甚至还没有意识到里面有 “TLDR” 的意味。最初它只是一个很小的绘图应用，更准确地说，是一个用于构建 infinite canvas 应用的开源库，类似 Miro 或 Figma 这样的画布体验。当时这个方向没有太好的开源基础设施，而他刚好有几个月时间，也非常沉迷这个问题，于是就做了出来。

这个小项目后来变得很受欢迎。很多公司和团队本来就想做类似的东西，只是一直觉得成本太高。它也吸引了 Adobe、Figma 这样公司的注意。主持人回忆说，他和 Steve 最早也是因为 Figma 对 Steve 感兴趣而认识的。当时 Steve 在纽约的一家设计工具公司 Play 工作，同时在 Twitter 上持续分享自己如何处理画布、形状旋转、箭头连接等细节。主持人说，Steve 几乎可以被称为“世界上最懂箭头的人”。

Steve 说，infinite canvas 是一个很难的领域。从设计角度、工程角度、性能角度，到多人协作和分布式系统，里面几乎都是硬问题。他当时会把自己调试和探索的过程发到 Twitter 上，比如形状要围绕自己的中心旋转，一组形状又要围绕整体中心旋转。就是这些细节吸引了很多人，也让他逐渐意识到，自己不只是做了一个玩具。

## 从开源库到公司

主持人回忆说，Figma 曾经想招 Steve，他在伦敦一家咖啡馆和 Steve 见面，才发现 Steve 是美国人，也是 fine arts 出身。聊着聊着，他意识到 Steve 对 tldraw 的投入远远超过对 Adobe 或 Figma offer 的兴趣。Steve 说，当时自己已经辞掉合约工作，准备全职做这个项目。就在他辞职后的第二天，一家大型电信公司联系他，说他们要做白板，想基于他已经做出的东西开发。

Steve 接受了这笔钱，但要求它必须是 sponsorship，而不是把 IP 交出去。他可以给对方源代码访问权限，每周沟通一次，但项目本身仍然属于自己。随后又有更多公司找到他，说他们已经讨论几个月甚至几年想做类似能力，但一直觉得太大、太难，现在希望直接基于 tldraw 做。到主持人和他见面时，这个雪球已经开始滚起来，Steve 知道自己要么把它卖掉，要么并入某家公司，要么干脆把它做成自己的公司。

主持人问，Steve 对 tldraw 的愿景似乎和传统 infinite canvas 公司不太一样。Steve 说，他并不是最早拥抱 AI 的人。他来自设计工具背景，长期使用 Figma、Whimsical、Miro 等协作白板工具，也关注 InVision Freehand 等产品。他一直觉得，人们真的很喜欢协作式 infinite canvas，至少喜欢它的人非常喜欢。但市面上的用例太保守，基本就是白板或设计工具。他看到的是一种二维直接操作界面，它本可以成为更多东西。

随着越来越多团队主动联系他，他意识到限制并不是大家不想做，而是 canvas 本身太难。就像很多工程师不会自己做地图、文本编辑器、data grid 或 UI framework，而是会使用已有工具一样，infinite canvas 也应该成为可以被复用的基础能力。Steve 当时甚至会在 pitch 里说，他不认为人们已经看到了 canvas 的 killer use case。

## 画布为什么适合 AI agents

Steve 说，他最初没有把 AI 放在愿景中心，但现在看来，很多适合人与人沟通的工具，也适合人与 AI 沟通。如果你想和很多人一起协作，白板是一种自然界面；当你想和很多 agents 一起工作时，白板也同样自然。

他描述了一个团队内部实验：公司 15 个人都在同一个白板上，每个人有三个小 agents 可以对话和指挥。这些 agents 是空间化的，它们在画布上有位置，并且有一种类似 foveated context 的上下文能力，也就是更清楚地看到靠近自己的内容，而不是同等关注整个画布。45 个小 agents 加上 15 个人同时在画布上工作，看起来很混乱，但交互上却显得正常。Steve 说，这个项目可以在 `fairies.tldraw.com` 体验。它看起来像卡通，但确实像是未来的一瞥：虚拟 agents 在画布环境中移动、执行任务、和人一起实时构建东西。

Steve 也承认，现在的模型还不真正擅长这种工作，所以他们把这些东西叫 fairies，而不是假装它们已经是有效的虚拟同事。但体验本身让他想起第一次使用 Figma 的感觉：你会立刻知道，这种东西会进入某些工作流。它适用于人与人的协作，也适用于人与 agents 的协作。

主持人问，在 tldraw SDK 之上，人们还做出了哪些实际用例。Steve 首先提到 Observable。Observable 原本更像一维 notebook，用来定义、处理和可视化数据。现在他们有 Observable Canvas，数据处理和可视化可以在二维空间里分支、延展、形成图结构。你可以从一个数据集出发，做查询，再向外做多个可视化或子查询。如果根节点发生变化，变化会沿着图传递到叶子节点。

Steve 觉得，这种体验和设计师在 Sketch 或 Figma 里做迭代很像。一个 Figma 文件最终常常像一张图，因为设计师会快速生成分支、比较方案。数据分析也是如此，重要的不只是最终图表，还有你怎么走到那里、做过哪些决定。有一次 Observable 团队给他演示两个基于同一数据的可视化，他建议把上面那张图透明度降到 50%，拖到另一张图上方，于是突然出现了一个大家都没专门设计过的功能：视觉上叠加比较两张图。这个例子让他觉得，画布媒介会自然产生很多这种涌现功能。

他还提到，有些大型应用里偶尔需要一个设计工具，但它不是整个产品的核心。比如一家做国际直邮物料的公司，需要把同一设计转换成不同语言和货币格式。文本长度变化后，设计需要微调，但这只是复杂物流流程里的一个环节。要单独为这个环节做一套 UI 很重，tldraw 则可以直接嵌进去，解决这个“局部设计工具”的需求。

## SDK 边界与商业模式

主持人问，作为横向基础设施，tldraw 怎么决定哪些能力应该被内置，哪些应该留给客户自己的应用。Steve 说，这很难。客户有时会认为某些能力是 undifferentiated，自己不想做，希望 tldraw 做；但 Steve 未必同意它们完全没有差异性。后来他学到，这类客户不想做但愿意付费的能力，往往就是所谓 enterprise features。

难点在于，要把不同客户提出的需求综合成底层模式。一个人想要测量工具，一个人想要更好的 grid snapping，另一个人想在 Web editor 里做 overlay。Steve 需要眯着眼睛看这些需求，判断它们是不是同一个“custom geometry overlay”类问题，然后尝试做出更通用的解决方案。

tldraw 本质上是一个 NPM package，用户安装后就可以在 Web 应用里使用。Steve 说，这种东西的商业模式并不常见。通常 NPM 包是开源的，公司在其上做产品。但 tldraw 采用 open core 模式，并试图为最核心的 IP 收费。用户可以拿 trial license key 试用 100 天。小团队可以购买几千美元级别的 license；大公司则和销售团队谈价，网站上没有公开价格；独立项目或 side project 可以拿 hobby license。

Steve 觉得他们很幸运做了这个选择。因为在 AI 出现以后，仅仅围绕开源项目做上层产品的模式变得更脆弱。主持人问，在 AI 可以不断复制软件的新市场里，tldraw 这样的公司到底在卖什么。

Steve 说，他确实预期到有一天销售流程会端到端和 agent 谈，包括价格谈判。但他也承认，自己的判断可能受自身利益影响。他对客户团队的核心论证是：你们当然可以自己做，优秀工程师理论上能做出类似 tldraw 的东西；问题是你们通常不会真的把它做到同样深。做一个产品的局部模块，和做一个 SDK 的动机完全不同。如果只是做自己的数据可视化画布，你会跳过很多边界问题，因为那不是你的重点；但做 SDK 时，tldraw 的目标就是把这些底层问题尽可能解决好。

所以，客户买到的不只是“今天就能用”，还买到一个比他们自己需要深入得多的底层，并且这个底层会持续变好。AI engineering 会改变一部分情况，团队可以让 agents 生成一个画布，但那很可能只是表层解决方案。如果这个底层对用户体验不重要，那当然可以自己做；但如果它会影响产品质量，最好让 agents 构建在一个已经被证明好的基础之上，而不是连底层也临时生成。

## 画布交互里的品味与决策

主持人说，tldraw 正在把一些 infinite canvas 的最佳实践编码下来，甚至变成图表和交互式 diagramming 的通用语言。他问 Steve 接下来半年到一年想把它带向哪里。Steve 说，目标一直是综合出这个 UX 范式里的模式。Infinite canvas 已经足够商品化，很多人看到它就知道大概怎么用：点击选择，按 Shift 多选，按 Alt 拖动复制。但真实产品之间仍有大量变体，每个细节都可能不同。

Steve 意识到，自己做的许多 UX 决策会传播到成百上千个产品里。主持人问，这些选择是怎样做出来的，是不是像一个 benevolent dictator。Steve 用和妻子玩 Lego 的例子解释：如果他伸手去“修正”对方搭的东西，从结果上看也许更好，但玩 Lego 本身是一种游戏，社交上这么做并不合适。可是作为创始人，情况不同。这里确实关心最终产品。你会消耗社会资本，也会让人觉得你太执着，但你必须这么做。

Steve 说，自己属于“impose your taste”的阵营。不要恐吓别人，但产品最终确实要好。tldraw 卖的是代码产品，代码本身也是产品表面的一部分，所以 API、命名和开发者体验都要有观点、要合理。他承认团队里也会有人问，为什么一个已经能工作的东西还要继续纠结细节。但他的回答很简单：他想让它好。

这种态度也影响招聘。Steve 说，招聘很难，但他倾向于在所有岗位上寻找同一种基础 profile：大体 full-stack，至少在多数技术领域有能力，通常偏前端，同时在某些地方有尖峰，比如设计、基础设施、开发者体验。他尤其喜欢有过产品 ownership 的人。开源维护者是很好的例子，因为他们必须面对社区，处理不是自己造成但仍属于自己的问题，给项目命名，做 logo，对整个东西负责。

他觉得，很多人在大公司里可能可以长期不需要让某个作品真正表达自己。但他想找的是对一个东西有个人关系、愿意站在背后的人。

## 从艺术到设计、代码和创业

主持人随后问 Steve 的背景。Steve 本科和研究生都学 fine art，曾经是实践中的艺术家，也写了很多关于艺术的文字。作为 day job，他做过类似律师研究助理的工作，也帮别人做或维护一些很轻量的 WordPress 作品集网站。后来他搬到英国，原来的工作因为法律环境不同而无法继续。他仍然有工作室，还在创作，但毕业几年后开始想把视觉创造力和更分析性的工作结合起来，于是转向设计、产品设计和 prototyping。

这个转向非常有意而为。他回看早期笔记时，发现自己当时几乎是激光一样对准目标。他说，如果要关闭工作室、转行，他不想只是成为“画矩形的人”。艺术家的训练给了他很强的能量：很多艺术家即使白天工作 40 小时，也会再花 40 小时在工作室里。那不是轻松的工作，而是智力和精神上都很难的工作。你每次都试图做伟大的东西，并且大多数时候失败。Steve 把这种能量集中到新的目标上。

他当时选择的切入点是 Framer Classic 和 CoffeeScript。那时这种让设计师用代码做交互原型的方式开始流行，Airbnb、Facebook、Uber 等团队都在用。Steve 觉得，没人真的会这个，那就让自己成为会的人。于是他的职业很长时间都围绕“能 prototyping、能和代码一起完成设计的设计师”展开。

他不喜欢把设计稿扔过墙给工程师，然后等工程师说这些东西在真实交互里不成立。更好的方式是在早期快速走几轮，把流程、交互和可用性先摸清楚。Steve 觉得，这种训练非常适合创业：一开始没人用你的东西，你有很大许可去试、去扔掉代码、去改进，而不是因为已经 ship 就停下来。

他还提到一种心理技巧：如果你能骗自己进入一种“我只是表演性地做一下”的状态，就会更自由。像 Dr. Seuss 用笔名写作，因为他总觉得以后还要写真正的伟大小说，结果这种距离感反而给了他创作许可。

## AI 时代，设计会怎样变化

主持人说，Steve 和他都属于“会 ship 的设计师”这一派：通过制作来学习，直接面对现实，而不是只在安全的塔楼里讨论。新技术正在改变很多设计假设，他问 Steve：AI 和 general intelligence 之后，设计会发生什么？

Steve 说，并不需要等到 general intelligence，设计已经被显著改变了。他提到 Jenny Wen 在柏林的演讲，以及她后来上 Lenny 的播客讨论设计流程变化。过去行业里有一场“设计师是否应该写代码”的争论。现在答案以另一种方式出现了：你不需要训练所有设计师写代码，也能进入一个设计师可以 ship 的世界。Steve 说，他的销售人员都在 shipping internal tools，这很奇怪，但也很惊人。

他认为，关键不是“设计师是否会代码”，而是把最有上下文、最适合做决策的人放到能真正做决策、进入反馈循环、影响产品的位置上。过去行业试图通过设计流程、设计师和工程师 pairing、混合团队来解决这个问题。但 Steve 观察到，很多团队里最酷、最好的功能，往往来自一两个人埋头做出来，然后再去争取许可或请求原谅。

他不认为未来完全没有设计流程，但如果设计这个职业想继续存在，就必须让优秀设计师进入更直接影响产品的位置。或者，也可以接受软件由有良好视觉判断的开发者、style guide 和 AI agents 一起完成。最好的设计师必须参与快速迭代，因为这个循环会变得非常快。“让我先 mock 一下给你看”的时代正在结束，至少日常大量设计工作会被这种更直接的方式取代。

Steve 说，他曾经有两位很好的设计师，后来让他们离开，因为团队的工作方式已经不再适合那种角色。他会更需要前面描述过的同一类 profile，只是这个人在设计上有更强尖峰。这样的人对公司的影响不是两倍，而可能是一百倍，而且工具每周都在变得更强。

他也承认，并不是所有设计都能由两个人晚上七点以后快速 ship 完成。用户研究、横向研究和一些更复杂的问题仍然需要不同方式。但相当一部分日常设计工作确实会被新的工作方式替代，而且应该被替代。

## 小公司怎样靠人格和正在构建的过程区分自己

主持人最后问，在这个新世界里，创业公司如何差异化。tldraw 的一个特点是，Steve 的人格几乎穿透了产品、营销、语言和 Twitter 内容。它不只是功能，也让人感到一种创始人的品味和真实性。Steve 说，他曾经在 Framer 做 design educator，类似技术设计师方向的内容和 devrel。他当时很努力地想搞清楚，怎样让人们关心一个技术产品：是视频、博客，还是别的形式。但那份工作最终没有做成，他没有找到答案。

后来他从中学到的是，小创业公司不应该幻想靠内容 backlog 慢慢积累。你拥有的是现在。你今天拥有 now，明天再重新拥有 now，然后不断追逐正在燃烧的引线。人们不会因为翻一个创业公司博客归档而突然关心你。要持续讲述故事，最好的材料就是你自己正在构建产品的过程。

Steve 经常发 GIF，不是因为他专门花时间做内容，而是因为这些 GIF 本来就是他调试、写 PR、做视觉工具时的副产物。有时他尝试写一条关于 API 设计的帖子，写到一半发现自己不好意思发，因为 API 还不够好，于是回去把 API 改好，再发更好的内容。这个过程反过来照亮了很多不明显的设计挑战：箭头怎样绕过容器、为什么某个工具里的箭头看起来别扭、压感墨迹应该怎样表现。

当时 Steve 甚至还没有计划把 tldraw 做成公司，他仍然想开源以后去 Adobe 或别的地方工作。但这种公开构建过程意外成了很好的产品营销。它让他建立了一种声誉：这是一个比其他人更在意箭头、画布交互和数字墨迹细节的人。如果你要基于某个画布工具构建产品，这种声誉非常有价值。

Steve 说，他很喜欢在 Twitter 上看到那些对某个问题空间极度痴迷、讲个不停的人。只要他们能把自己的痴迷讲得让外人也关心，就会形成真正的信任。就像高端餐厅里的许多选择，普通人未必逐项注意，但桌子、灯光、呈现方式、服务路径都在累积成体验。软件里的硬问题空间也是如此。所谓 taste，不是天生的神秘能力，而是在一个领域里做出有信息、有观点的选择。

在 tldraw 里，这种选择可能具体到虚线拐角处的 dash 要不要锁在角上，间距怎么变，线段怎么连接。每个细节都很小，但它们累积起来形成产品的状态。主持人最后说，任何用过 tldraw 并在其上构建东西的人，都会感受到这些细节如何累积成一种 state of the art。节目也在对 Steve 的掌声中结束。
