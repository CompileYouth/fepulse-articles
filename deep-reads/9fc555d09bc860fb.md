节目开头先抛出一个一年后的想象。Anthropic 平台团队希望探索这样的方向：Claude 足够理解自己，能够判断应该用哪个模型，怎样启动 sub-agents，怎样选择架构。用户不必再思考那么多 harness engineering，因为 Claude 能在运行中根据任务把自己和 agents 改造成需要的形态。如果 agent 能 on the fly 地变成需要变成的东西，平台就必须严肃扩展，承载这种不断运行、不断重组的工作负载。

主持人 Dan Shipper 开场介绍，Angela 是 Claude platform 的产品负责人，Caitlyn 是 Claude platform 的工程负责人。Anthropic 最近推出了 Claude Managed Agents，并继续发布新功能。Dan 想讨论一个更底层的问题：对于模型公司来说，AI platform 到底是什么。

在 GPT-3 时代，platform 主要是 completion endpoint：发送 prompt，拿回 response。后来它变成带 tool calling 和 chat sessions 的 completion endpoint。而现在 Claude Managed Agents 更像是给你一个在云里运行的 Claude，有电脑、有内存、有工具、有状态。Dan 希望两位解释这条轨迹，以及“构建 AI 平台”今天意味着什么。

## 平台从 token endpoint 变成 outcome infrastructure

Angela 说，这个描述很准确。最早把 LLM 放到 API 后面已经很令人兴奋，但今天回看会觉得那很基础。随着模型变得更自主，平台逐渐从无状态的 token in/token out，走向更 stateful 的世界。用户希望 session state 能被持久化，希望模型表现更好，平台就需要提供更高阶抽象。

她认为，贯穿始终的是一件事：帮助用户从 Claude 获得最好结果。早期大家不知道会用 LLM 构建什么，所以平台要尽量保留可能性。后来 use cases 逐渐变窄：有人构建产品，有人构建 agents。越来越多客户来问：怎样让 Claude 发挥最好？怎样设置工具？怎样运行 loop？有些人愿意在边缘探索，但大量用户想要 out of the box 的能力。

因此，Anthropic 不断把 platform 变得更丰富：状态、工具、云组件、基础设施都被纳入。最终，一个平台可能就是一组 primitives 和 infrastructure，让用户以最少工作、最快获得 outcome。

Caitlyn 解释 Claude Managed Agents 里的 primitives。它建立在 Messages API 上，仍然可以只是 tokens in and out，但 Anthropic 在 API 周围加了很多能力：built-in tools、code execution、sandbox、web search 等。Managed Agents 把这些强 primitives 组合成一个 harness 和基础设施，Anthropic 认为这是让 Claude 产生最好 outcome 的方式。

## 为什么 Anthropic 要自己做 managed agents

Dan 说，他有一种“time deflation”的感觉：自己的时间未来会更值钱。Every 内部也在构建 agent products，甚至有 Mac mini 上跑着 Claude loop，还有几千行 Python。很多这类工作看起来和 Anthropic 在 Claude Managed Agents 里做的很像，所以他会想：是不是应该等 Anthropic 做完，而不是自己重复构建。

Angela 说，这正是平台业务常见的问题。客户有立即需求，于是自己做；但也担心平台很快免费提供同样能力。Caitlyn 补充说，Anthropic 自己也经历过足够多次“为内部产品搭 autonomously running cloud agents”的基础设施，最后决定不再重复造，而是正式做一套能从内部经验中沉淀出来、也供外部用户使用的基础设施。

简单在几台 Mac mini 上跑 agent 可以工作，但如果要把 agents 集成进产品、面向大量用户运行，基础设施难度会急剧上升。要处理运行时、沙箱、持久化、断连恢复、扩缩容、凭证、安全等问题。Anthropic 做 Managed Agents，就是为了让用户不再把工程资源花在这些基础设施上。

Angela 说，Managed Agents 的设计里有两层哲学。第一，Anthropic 会对一些和 Claude 很强绑定的部分保持 opinionated。例如，他们希望 Claude 使用文件系统，也非常重视 skills。这些 primitives 看似基本，但 Anthropic 认为它们对 Claude 做好 agent 工作很关键。第二，平台也会尽量保持开放。很多 API 未来会在不同地方打开，让用户能加入自己的部分。Anthropic 也会发布 blog posts 和 reference implementations，用户如果想在 Messages API 上自己做，也可以借鉴这些结构。

## generic harness 不一定是未来

Dan 说，Every 团队担心使用 Managed Agents 会产生 lock-in。现在他们自己的 Mac mini 或 cloud setup 很灵活，可以让 Claude 做任何 Claude Code 能做的事，也可以较容易换成 GPT-5.5、Gemini 等。团队担心，如果换到 Claude Managed Agents，就没有那么多灵活性；而且 Claude Code 的新功能也许会先到一线产品，再过一段时间才进入 Managed Agents。

Caitlyn 解释说，Anthropic platform 团队不仅做外部 API，也做内部 platform。Anthropic 的第一方产品都建立在同一平台上。因此，platform 团队会和内部产品团队一起工作，支持它们构建功能。长期看，Claude Managed Agents、co-work、Claude Code 等之间的差异会减少，因为它们会越来越多地坐在同一基础设施上。

Angela 承认 model lock-in 的担心合理。但她认为，几个月前很多人会做非常 generic 的 harness，再在下面热插拔模型。对旧一代模型来说，这还算合理。现在每个 lab 都在用不同技术和视角推进模型，模型与 harness 的关系越来越紧密。如果你为公司或客户构建 agent，最终要交付的是 outcome。此时抽象层可能不是“一个 generic harness + 可替换模型”，而是“harness + model 作为一个 agent 单元”来替换。你仍然需要 redundancy，也会在不同任务上用其他模型，但不是每个底层组件都完全 generic。

她举 memory 为例。Anthropic 为 Managed Agents 做 memory 时，内部试过很多 harness。不同 harness 在 eval suite 上表现差异很大。只要把正确组件组合起来，就能通过 harness engineering hill climb 很多性能。这说明，哪怕只是请求响应、tool calls、文件系统等看似小的选择，也会改变模型轨迹。

Angela 也认为，路径依赖会锁定模型行为。某些时代的模型会过度优化 reasoning，另一些则可能更强调 computer use。Anthropic 必须非常认真地选择给模型哪些 native primitives，因为这些选择会影响未来能力形态。

## Managed Agents 面向谁

Dan 回到一个基础问题：Claude Managed Agents 是给谁用的。他自己当天设置了一个 agent，还用 Codex 的 in-app browser 驱动设置流程，很快就做出了 Slack bot。他感觉即使非技术用户也可能想用它。

Caitlyn 说，quick start experience 的目标不是专门服务非技术用户，而是让任何人都能理解 primitives：它能做什么、怎么组合。整体看，Managed Agents 有几类目标用户。

第一类是公司内部想构建自动化、内部平台或内部系统的人。比如想要一个端到端 software development platform，或者想自动化某个流程，例如 legal review marketing copy。用户不应该为了这些场景重复实现 memory、sandbox、long-running agent 等基础设施。

第二类是把 agents 构建进自己产品、交给客户使用的人。这类用户仍然需要大量 customization，也要做真正符合自己产品体验的设计，但 Anthropic 认为他们不应该把工程资源花在基础设施和细碎 harness tweaking 上。

主持人问，人们以为难点是什么，最后真正难点是什么。Caitlyn 说，很多人以为 hardest part 是 harness engineering：prompt caching、最大化 context window、tool 调用等。Anthropic 过去推出 Agent SDK，就是为了降低这部分门槛。但很多客户在要把 agent 投入生产、扩展规模时，会撞上 infrastructure wall。要有长期运行的 server 或可伸缩运行时，要存 transcript data，要做 secure sandboxing，要保证 sandbox 断连后 agent 不会直接死掉。对于更有趣的 long-running async agents，这些基础设施尤其难。

## 从个人 agent 到团队 agent

Dan 提到 OpenClaw 带来的一个形态：始终在 Slack 里存在的 agent，有自己的 personality，也有自己负责的世界。Anthropic 是否会让用户一键把 agent 部署到 Slack，而不是手动做大量设置？

Angela 说，这正是他们想做的方向。Managed Agents 先从基础设施痛点开始，但 advanced shape 肯定包括非常容易部署的 agents。Anthropic 已经在一些底层 primitives 上走了第一步，比如 vaults，用来存储凭证和 OAuth keys。等 agent identity 相关 primitives 更安全、更顺畅之后，可能会出现一键 Slack integration，甚至只是告诉 Claude“加上 Slack”，它就处理完所有事情，然后 bot 开始在 Slack 里提醒你。

Dan 问，内部 agents 的最佳 use cases 是什么。Angela 提到 Stripe 的 Minions、Ramp 的内部系统，以及 Anthropic 自己也有类似平台。对于单个人，Claude Code 很好；但如果是端到端开发平台，需要把公司 CI/CD、开发环境、验证方式等定制进去，就适合在 Managed Agents 上再薄薄构建一层。

Caitlyn 进一步说，个人 productivity 很多工具已经很强，但一到 team layer 就复杂得多。一个 agent 不能只坐在某个人笔记本上。三个人想让几个 agents 互相配合，自动化一整个流程，就需要更高层抽象。复杂流程如果要被 AI 真正改造，往往需要 team orientation，而不是单个 agent。这需要一个可以由团队共同启动、关闭、控制和协作的平台。

## Legal review marketing copy 的例子

Anthropic 内部一个简单但有用的例子是 legal review marketing copy。过去 marketer 写完 copy 后，可能要开 ticket 请 legal review。现在可以提交给一个小 app，先由 legal reviewer agent 做第一轮检查。Agent 可能直接判断 marketing 可以通过，也可能把需要人工审核的内容放进 legal inbox。

Dan 问，这为什么不是一个 skill。Angela 说，它可以包含 skills。比如 legal reviewer agent 会有 MCP servers 去访问外部上下文，也会有 skills 告诉它公司规则、哪些能说、哪些不能说。但它不只是 skill，因为还需要正确的 form factor：不同人要协作，agent 要独立运行 session，有时还需要多个 agents 参与。而且 legal 这类流程需要 human in the loop，有认证和责任边界，不能只是一个本地 skill 一次性运行完。

Dan 接着问，这类 agent 建好后谁拥有它。因为如果没有人负责，agent 很快会 stale。Angela 说，Anthropic 最初由一个团队构建 app 和流程，然后交给使用方。但很有意思的是，使用团队的人会发现某些地方想改，于是打开 Claude Code 自己提交 PR。平台团队仍然负责 review 自己拥有的系统，但业务团队可以 self-serve 地改进 agent。

为了避免非技术用户直接在底层代码里误操作，他们也做了几层抽象。有些团队通过另一个 Claude 实例和 agent 交互，由 Claude 判断应该怎样改底层 agent。这其实是 Managed Agents all the way down：终端用户感觉是在简单和 Claude 聊天，底下则是多个 Claude 彼此协作，执行复杂工作。

## 多 agent orchestration 和架构策略

Anthropic 最近推出了 multi-agent orchestration。Caitlyn 说，有趣用法之一是构造不同 harness techniques。比如把 execution 和 advice 分开，让一个 agent 执行，另一个 agent 提建议；或者一个生成，一个 adversarial review；或者把问题拆成很多小块再重组；或者做 best-of-N 风格的策略。

不同架构适合不同场景。深度研究或广度研究，可能适合某些分解方式；bug hunting 可能适合 agents 一起 swarm。Caitlyn 希望 primitives 像 Lego 一样可组合，这样用户能在更高形态上组合出 architecture 或 strategy，而不仅是单个 agent。它也意味着可以在多个抽象层 hill climb：不仅优化 prompt，也优化 agent 结构。

Dan 问怎样衡量 agent 成功。Caitlyn 说，evals 当然存在，但 Anthropic 更喜欢朝 verifiable outcome 方向走。理想终态也许是，用户只给 outcome 和 budget，其他都由系统解决。Coding evals 里可以用 PR 是否 merge 等可验证结果；更高层任务中，outcome 可能是人能定义的一份 spec，系统需要反复解释、评价和修正自己，直到接近目标。

Dan 开玩笑说：“Claude，让我赚 10 亿美元，预算 10 美元。”这也正是他们想压缩到的形态：结果、预算和少量约束。

## Agent 生命周期和升级

Dan 提出另一个实际问题：agents 会很快过期。可能因为没有人负责，可能是旧模型、旧架构、旧工具。Every 甚至开玩笑说要给 decommissioned agents 办一个小 funeral 或建页面。怎样管理这些散落在 Slack 里、每周还会 ping 一下但明显 stale 的 agents？

Angela 说，Anthropic 已经做了一些 skills，帮助用户在新模型发布时升级 agent。她认为最常见的 lifecycle 问题就是新模型出来后，要迁移、升级，或者干脆用新模型构建更强的 agent，把旧 agent 退役。这类似 breaking change，需要实际投入。evals 会让迁移更容易。更激进的人甚至会用 agents 监控 agents，判断哪些 agent 已经过时、需要升级。

## 一年后的平台会怎样

最后，Dan 问一年后 Claude platform 会到哪里，用户能做什么。Angela 说，一年在这个行业很长。她希望平台更接近一个状态：用户只要给 outcome 和 budget，Claude 能理解自己，选择合适模型，启动 sub-agents，决定 architecture，不再让用户操心太多 harness engineering、tool construction 和 prompt engineering。今天很多创新仍发生在高层 harness architecture 上，但如果继续往上走，这些复杂性应该逐渐消失。

她不确定一年内能否完全到达，但希望至少在 outcome 维度上大幅推进，budget 维度再带一些误差条。

Caitlyn 给了一个更工程化的答案。如果 Claude 和 agents 能 on the fly 地变成任务需要的形态，平台就必须能够严肃扩展。它要承载大量 tokens 的进出，要处理常驻 agents、长时间请求、不同形态的 workloads。平台本身不能成为用户完成事情的瓶颈。因此，未来一年平台团队很大一部分工作，就是设计正确抽象，并确保系统能 scale 到这种 constantly running、constantly recreating agents 的世界。

整场对谈最后回到最开始的问题：AI platform 不再只是一个模型 endpoint。它正在变成一组能让 agents 持久运行、协作、使用工具、管理状态、接入团队流程并交付 outcomes 的基础设施。模型越自主，平台就越像 agent operating layer，而不是单纯 API。
