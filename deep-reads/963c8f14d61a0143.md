节目开头先给出 Gary Tan 的核心判断：接下来最重要的问题之一，是你能不能控制自己的工具，还是你的工具反过来控制你。他形容今天使用 OpenClaw 像开一辆 Ferrari，非常刺激、非常疯狂。它能快速想明白很多过去很难想象机器能想明白的事。但它也像 Ferrari 一样，你最好自己也是机械师。它会在最需要的时候坏在路边，你得拿扳手打开引擎盖，自己把它修好。

主持人介绍说，这是一期 Lightcone 特别节目，要聊 Gary Tan 怎样重新开始构建。如果关注他们的 Twitter，就会知道 Gary 在做了多年投资人之后，又回到了 builder 状态。过去几个月里，他 ship 了几十万行代码，做出了一些受欢迎的开源项目，其中有项目从零涨到 GitHub 上超过 10 万 stars。而这一切发生在他全职管理 YC 的同时。很多互联网上的人不相信这可能，但他们亲眼看到了全过程。

Gary 说自己也很震惊。他 13 年没有写代码，然后突然之间，自己一年的工作量变成过去写代码时的大约 400 倍。

## 从 Gary's List 重新开始写代码

主持人把话题拉回最早的项目 Gary's List。Gary 说，那是在一次 Lightcone 节目之后。他意识到自己想把一群相信相同理念的人聚在一起，特别是围绕 California 的问题。他开始做一个 501(c)(4)，后来又发展成 C3 和 PAC。这是政治组织常见的结构，但 Gary 强调，大家总关注钱，而他真正想做的是把聪明人聚在一起。

他在 San Francisco politics 里学到的一点是，把人连接起来非常有力量，这就是群众运动的本质。于是他想，为什么不做一个网站来开始做这件事？第一步就是写自己担心的问题。

他举了代数教育的例子。世界各地的观众也许会觉得奇怪，但在 San Francisco 公立学校里，七八年级学生想学 algebra 仍然很难。Gary 说，如果他小时候在 Bay Area 的公立学校里没有机会学 algebra，他后来不可能去 Stanford 学工程，也不可能写代码，不可能做现在这些事。所以这个问题对他很私人。

这时他意识到，是时候重新写代码了。他回顾自己第一个 YC startup：Posterous。那是一个通过 email 发布的极简博客产品，后来成长为互联网前 200 的网站，被 Twitter 以大约 2000 万美元收购。Twitter 收购后关闭了 Posterous，Gary 没有足够的钱把它买回来，于是后来又和 Brett Gibson 做了 Posthaven。

2026 年 1 月，他第三次重写了类似的东西。第一次 Posterous 花了大约 400 万美元、六七个人和一年半。第二次 Posthaven 花了大约 10 万美元、两个人和三个月。第三次，他用 Claude Code Max 账号，成本大概 200 美元，花了五天，做出一个完整博客平台。

这个平台不只是普通博客系统。它还有完整 RAG 和 agentic retrieval，可以读互联网上的内容、读取他过往所有 tweets，对任何主题做 recursive crawl 和 deep research。Gary's List 会围绕 California、San Francisco、LA 和更好政府等议题，每天产出两三篇有研究、有来源的文章。

主持人指出，很多人没完全理解 Gary's List：它既是 blogging platform，又在做高质量 investigative journalist 的工作。不是记者用来发布文章的工具，而是工具本身会做记者的一部分工作。Gary 说，以 5 到 10 美元的 Opus 调用成本，就能完成一个人类需要 painstakingly 阅读几十篇文章、整本书、做注释才能完成的工作。

他从 Casetext 创始人 Jake Heller 那里学到一个重要思想：要思考人类拿到上下文后会怎么做。人类会检索什么？会去图书馆找什么书？会在网上搜什么？今天可以调用 Perplexity API、X/Grok API 等，把大量上下文抓回来。Gary 把这称为 boil the ocean：写 agentic software 时，不必再满足于过去人类写代码时能手工处理的范围。只要增量工作能让结果更完整、更准确，就应该多花 token，把上下文补足。

他认为 token maxing 不只适用于文章，也会进入代码和所有知识工作。它不会消灭人，而是要求人继续提供 agency。比如 Gary 自己关心 algebra，是因为他真正在乎那些本来可以学代数、却被制度挡住的孩子。技术的大变化出现时，人仍然要把自己的痛点、需求和意愿放进去。

## 从重复提示到 GStack

Gary's List 的构建过程让 Gary 发现了一批新模式，也引出了下一个项目 GStack。他说自己一开始并没有计划做 GStack，只是发现自己在 Claude Code 里反复输入同样的东西，于是把这些内容写进 Apple Notes。

其中最早的模式之一是 plan review。他喜欢让 Claude 先画 ASCII diagrams。过去 Claude 有时会迷糊、写 bug 或不完整。但当他要求它在开始前先画出所有数据流、输入输出、用户流程、错误信息，或者画出 state machines、dependency graphs、processing pipelines、decision trees 后，Claude 会把上下文加载得更完整，工作也更完整。

这些后来变成了更结构化的检查：architecture review、code quality、tests 等。Gary 说，自己手写代码时往往只做最低限度测试，因为测试没有那么有趣。但 vibe coding 后，他很快遇到大家都会遇到的问题：80% 情况能跑，但真实用户一碰就倒。于是他意识到，可以让 AI 帮自己逼近很高的测试覆盖率。后来他又认识到，100% 可能太多，80% 到 90% 通常更合理。

他还提到 office hour skill，这个技能模拟他们和公司一起工作的过程：怎么知道用户想要这个？它为谁服务？做什么？影响是什么？但 plan review 是更早的 proto skill。那时他还不知道 skills 这个概念。后来他发布了这个内容，吸引了很多关注。他又做了更扩展的版本，叫 mega plan，后来改名叫 CEO plan。

CEO plan 用了 metaprompting。Gary 把已有 review plan 拿来，让模型想象 Brian Chesky 坐在旁边。Chesky 常讲“10-star experience”：大家通常只想五星体验，但可以继续问六星、七星、八星甚至十星是什么。Gary 很喜欢这个产品和设计练习，现在可以每次都让 AI 做。这个 prompt 还会问 10x check：有没有更有野心、只多花 2x effort 却带来 10x value 的方案？

Gary 说，自己是 ADHD CEO，喜欢潜力和纯粹的可能性。一个很短的 prompt 就能解锁大量思考。GStack 最初只是一些 skills repo，但很快变成了他的日常工作系统。

## Conductor、QA 和让 agent 自己检查 UI

Gary 展示自己在 Conductor 里的真实工作流。他会把各种想法排队，使用 CEO skill 做计划，让另一个 skill 帮忙把测试做扎实。计划通过后点击 approve，Claude 就会去做事。他这么做太多，以至于经常有十几个 feature 都排队等他手工测试。

这些 feature 可能已经通过端到端测试、集成测试和单元测试，但他仍然需要打开 Rails server，加载特定用户、切到某个配置，手动确认它真的能用。他厌倦了这个流程。最初他尝试用 Claude in Chrome MCP，但每一步都要两三秒，太慢，不适合 QA。

后来他知道 Microsoft 的 Playwright，于是直接让 Claude Code 包一层 Playwright。他的请求大概就是：我受够了 Chrome MCP 太慢，能不能包装 Microsoft Playwright？这就发展出 GStack 里的 browse 和 QA。Browse 是一个 long-lived HTTP daemon，带有 70 多个 CLI commands；QA 则基于 browse，在 prompt 里要求它查看当前 branch 做了什么，如果涉及 UI 或数据 mutation，就用 browser 去测试。

Gary 说，第一次看到它像黑盒浏览器一样测试功能时很震惊，感觉 mini AGI 已经来了。虽然这不是真正的 AGI，真正的 AGI 是他完全不需要在场。但作为 builder，他希望人类永远还要在 loop 里。只要机器还没完全替代，人类工程师的 taste、design、product feedback 和真实客户理解就会像给他们装上翅膀。

## thin harness, fat skills

主持人提到 Gary 在 X 上写过 thin harness and fat skills。Gary 说，这部分也来自网上有人嘲讽他只是卖 markdown。但他的实际体验是，markdown 本身已经像 code，只是以不同方式被编译。现在可以通过 markdown 让电脑做很惊人的事。

他解释，harness 是核心循环：接收用户输入，把它交给 LLM，运行 LLM 的工具调用和行动。既然 Claude Code、Codex 等已经是很强的 harness，为什么还要一遍遍重写？真正应该花时间思考的是：应该有哪些 markdown？如果你是婚礼策划师，要写一份 checklist 教下一个人怎么再办一次婚礼，你会用自然语言写下哪些步骤？这些就应该在 markdown 里。

而那些必须确定性执行、或者是真实行动的东西，就不该放在 markdown 里。比如婚礼策划师可能要给 20 个场地打电话，这种动作应该调用 Twilio 之类工具。Gary 认为，当今 agentic engineering 的很多困难，都来自把本该写在 markdown 里的东西写成 code，或者把本该 deterministic 的东西交给 LLM。

Code 是脆弱的，不理解特殊情况，也不理解你是谁、你想要什么；它只是执行确定性的 0 和 1。而 LLM 有 latent space，知道你的动机，可以处理泛化情况。工程上的魔法就在于判断：哪些东西应该在 LLM land，哪些东西应该在 code land。

再加上 80% 到 90% 的测试覆盖和 boil the ocean，就能减少 slop。Gary 说，如果没有测试就把用户扔进去，AI 写出的代码可能比人写的糟糕 10 倍，因为你完全不知道会发生什么。机器不怕做更多测试，它会继续做。OpenClaw 现在还有很多 failure cases，但已经 95% 可用。

## OpenClaw、个人 AI 和 token maxing

Gary 再次用 Ferrari 类比 OpenClaw：它让人兴奋，能做很多不可思议的事，但你必须能修。现在像 Homebrew Computer Club 时代，像 Apple I 刚出现时那样，个人电脑需要懂技术的人自己折腾。今天要让这些 AI 系统跑起来，也需要懂技术的人花两三个小时、花几百到一千美元的 tokens 和 cloud 成本。但一旦跑起来，就像拿到一辆 kit car Ferrari，可以开去任何地方。

主持人说，过去从 Stack Overflow 到 ChatGPT，再到 Claude Code，是一个很快的变化。Stack Overflow 已经让人觉得神奇；ChatGPT 让问答更互动；Claude Code 则让人不再复制粘贴，而是让工具直接执行和运行代码。OpenClaw 也类似，虽然可能把自己搞坏，但只要旁边有 Claude Code，它又能修自己。

Gary 说，自己一开始完全是 Claude Code 派，现在仍然大量使用，但可能只有 50% 到 60% 的 product building 或 agentic engineering 时间在 Claude Code 里，另一半逐渐转向 OpenClaw。GBrain 就是在这种探索中出现的。

他第一次真正开始探索 OpenClaw，是在 Karpathy 讨论 knowledge LLM wikis 时。Gary 有一个 markdown repo，里面放了大量自己的 context。他发现 OpenClaw 用的模型和 context 加载方式不够好，于是陷入 rabbit hole：用 Conductor quick start、GStack，开始构建 GBrain。

他并不是从零开始。他在 Gary's List 里已经学过 vector embedding、hybrid RRF、chunking 等，因为他需要做一个 agentic newsroom，文章要达到特定质量、包含 citation。他把这些经验抽取出来，用到 OpenClaw 的 full RAG system 里，选择 Postgres 和 pgvector。Gary 认为，这也是为什么现在可能进入开源黄金时代：任何人都可以让 agent 去看自己已有项目里怎么做 chunking、embedding、RAG，然后抽出一套新系统。

## 400x、lines of code 和重新获得 builder 身份

OpenClaw 还能回顾 Gary 的记录。它显示，1 月 23 日 Gary 发过一条 tweet，说 Claude Code 唤醒了他 25 岁时那个喝 Red Bull、熬夜写代码的自己。主持人称之为 builder identity resurfacing。

Gary 说，他回到了每天睡 4 小时、写 20 小时代码的状态。这也让他在网上因为 lines of code 争议惹上麻烦。他说 lines of code 不能完全衡量开发者生产力，但又“某种程度上可以”。他用工具标准化 logical lines of code，去掉无意义差异后，发现自己不是 100x，而是 400x。原因之一是，他 2013 年自己写的代码被标准化后减少了大约 70%。

他承认，lines of code 容易引发误解，也不该用来 trolling。但背后有更深的事实：对技术人来说，这些工具确实大幅提高了能力上限。最容易在网上攻击 lines of code 说法的人，反而往往是最有 taste、最懂技术、最能从 token maxing 中受益的人。Gary 的建议是：别再抵抗，打开 Claude Code 试试。

主持人补充说，体验差异也和模型、harness 有关。同一个 Opus 模型，在 OpenClaw 里做稍复杂任务可能失败，但在 Claude Code 里效果更好。Gary 认为，这种“还不太行”的感觉会重演。今天大家可能觉得 OpenClaw 或 Hermes 还很折腾，但一年后，每个人都会有自己的 personal AI。

他认为，人们面前会有两种世界：一种是拥有自己的 AI、自己的数据、自己的 integrations，能看见系统怎样工作，自己写 prompts，并控制自己看到什么；另一种是 corporate controlled 的 AI，像 Facebook feed 一样，你不知道算法是谁写的、服务谁、背后商业模式是什么。

个人电脑革命给人类的礼物，是个人可以拥有自己的计算工具。Gary 认为 personal AI 会经历同样转变。除非你拥有自己的 prompts，并能为自己写 prompt，否则你就处在某个 PM 或 developer 写好的 API 之下，对方不了解你、你的需求和你独特关心的东西。决定性问题就是：你控制自己的工具，还是工具控制你？

## token 成本像 San Francisco 房租

主持人指出，普通公众可能没有意识到，要获得这些能力，通常必须使用最新、最强的模型，而且非常贵。Gary 说，这让他想起 San Francisco 的房租。很多 YC 创始人不想搬去 San Francisco，因为租金高。但他们常说：不住在那里更贵。早期创始人应该为靠近 serendipity 付钱。

Token maxing 对 founder 也类似。它不是桌子或沙发那种可以省的成本，而是像租金一样应该尽量投入，以换取最大效用。YC 的经典建议是 live in the future and build what's missing。今天这句话有了更深版本：你要能接受一天在 tokens 上花 500 美元，只要你在构建对自己真正有价值的东西。

主持人最后问，Gary 同时是 YC CEO，时间极其稀缺，这是否反而帮助了他？因为他没有全职工程师那样的大块时间，只能在会议间隙推动自己自动化一切。

Gary 说，他有时很羡慕 time billionaires。孩子们、很多 Startup School 的年轻人，拥有大量时间，可以学任何东西。他自己则觉得脑子里有一种疯狂紧迫感，好像要在这一具身体里活出 100 亿次生命，每一刻都要算数。Token maxing 让他可以购买机器意识的数百万年时间。那不是他自己的时间，而是机器为他工作的时间，服务于他关心的人和事业。

他关心 YC，关心 builder 能不能构建。他并不想把这一切说成宏大计划，但 Lightcone、Boris Cherny 说“我们团队不写一行代码”等经历，让他意识到自己也能做类似的事。他说，自己和观众没有不同。大家都有同样的 prompt、同样的 MacBook Pro。没有什么阻挡任何人调用数百万年的 tokens 去服务人类。

主持人把这总结为：人可以通过借用机器的时间，拥有近乎无限的时间。Gary 最后说，这是一个非常值得活着见证的时代。
