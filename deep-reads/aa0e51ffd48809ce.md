这条分享一开始，YC 的 Diana 先把自己的结论说得非常明确：过去几个月里，她越来越确信，AI 不只是会改变软件构建速度，也不只是会让某些工作流自动化，而是会直接改变创业公司应该怎么运行。她说，变化会涉及岗位会不会继续存在、产品还能怎么做、团队该怎么搭。整段视频她想回答的，就是创始人该怎么理解 AI native company，团队里应该有哪些角色，以及现在就能采取哪些具体内部做法来明显提速。

她先批评了一种现在很常见的说法：很多人仍然把 AI 理解成“生产力工具”，会一直讲它怎样让工程师更高效，或者说给现有工作流加一个 copilot、多发一些功能就行。但在她看来，这种说法抓错了重点。真正发生的变化不是简单的 productivity boost，而是全新的能力出现了。合适的人，加上 AI 工具，已经可以做出以前需要整支团队才能做出的东西，甚至做出以前压根不可能做出的东西。

接着她把问题推到组织层面。她说，如果从“新能力”而不是“提效工具”的角度看 AI，就会立刻带来一些关于公司该怎么运营的不同结论。她自己的总体判断是，AI 不应该只是公司在用的一个工具，它应该成为公司运行的操作系统。每一个工作流、每一个决策、每一个过程，都应该穿过一个持续学习、持续改进的智能层。

她随后引入了 open loop 和 closed loop 这组控制系统里的概念来解释。她说，旧世界里的公司基本上是在 open loop 模式下运作：你做一个决定，执行它，但并不会总是系统性地衡量结果，再根据结果去调整过程。这样的模式天然会丢失信息。closed loop 则不同，它会持续监控输出，持续调节过程，以便更接近目标。她认为，在有自我改进 agent 的前提下，公司就应该按 closed loop 来运行。

为了让这种闭环真的建立起来，她提出一个非常具体的要求：整个公司必须是可查询的，也就是整个组织要对 AI 可读、可见。她说，公司的每一个重要动作都应该留下 artifact，让公司中央那个智能层能够学习和持续改进。比如重要会议都应该有 AI 记录；尽量减少无法沉淀的私聊和邮件；在所有沟通渠道里嵌入 agent；公司里关于收入、销售、工程、招聘、运营等关键数据，都应该进入定制仪表盘。

为了让这个说法更落地，她举了工程管理和 sprint planning 的例子。她说，如果一个 agent 能看到 Linear 工单、Slack 工程频道、从邮件或 Pylon 之类工具进来的客户反馈、GitHub、Notion 或 Google Doc 里的高层计划、销售电话以及 daily standup 的录音，那么它就能判断上一轮 sprint 到底交付了什么，那些交付是否真的满足了用户需求。再往前一步，它还能利用这些上下文去提前提议新的 sprint 计划，而且会比靠工程经理层层汇总状态更准确、更可预测。

她说自己以前管理过工程团队，现在又在多个 YC 公司里看到类似变化，所以她很确定这是一件 game changer。以前需要靠大量协调才能推进的事情，一旦组织默认变得可读、可查，很多信息损耗就消失了。她甚至提到，自己见过一些团队用这种方法把工程 sprint 时间直接砍半，并在同样时间里做出接近 10 倍的东西。

她接着概括出一个更总的原则：如果你真想拿到模型的完整能力，你就得给它尽可能接近真实员工的上下文。只要做到这一点，公司就不再是那个信息碎片化、需要靠人手动解释的 open loop，而会变成一个 closed loop system。状态、决策和结果会持续被捕捉，再持续反馈进智能层，公司因此会一直拥有一个相对实时的全局视图。

然后她把话题推进到产品和工程生产方式本身。她说，现在正在形成一种新的高速度公司构建产品的范式，也就是“AI software factories”。如果你熟悉 test-driven development，她觉得这可以被看成 TDD 的下一阶段：人类写 spec 和测试集，定义成功标准，然后 AI agent 生成实现和代码，不断迭代，直到测试通过。人定义做什么，也判断结果好不好；真正写代码这件事则变成 agent 的工作。

她举的例子是 Strong DM 的 AI 团队。对方的目标几乎就是把人类亲手写代码和 review 的需要降到最低，于是他们做出了一整套 software factory：规格和场景化验证来驱动 agent 写测试、改代码、一直迭代，直到达到某个概率上的满意阈值。这在她看来，就是 Steve Jang 所说“千倍工程师”的一种现实版本：一个工程师被一整套 agent 包围后，可以完成原本根本不可能独自完成的事情。

接下来她把这个逻辑继续推到组织结构。她说，如果你的公司到处都有 AI loop、整个组织又默认可查询、工程生产又走向软件工厂，那传统的管理层级其实就不再合理了。旧世界需要大量 middle manager 和 coordinator，是因为信息要在组织里一层层传递，而且过程本来就很低效。新世界里，智能层本身就在承担一部分这类作用。如果公司已经对 AI 可读，而且有足够多 artifact，那么就不应该再有那么多“人肉中间件”。

她特别强调，公司速度的上限取决于信息流动速度。你每去掉一层人工转译，速度就会直接上一个台阶。她举 Block 里的 Jack Dorsey 作为例子，说他在认真研究这些工具之后，也得出了类似结论：如果公司还是原来的组织架构和管理结构，那就说明它根本没有理解这一轮变化。公司本身需要被重建成一个 intelligence layer，而人则站在边缘去引导它，而不是继续亲自做信息路由。

最后她引用 Jack 对未来公司员工类型的一个划分。第一类是 individual contributor，也就是 builder/operator，直接做事、直接运营，不只是工程师，支持、销售、所有人都要来会议时带着可运行原型，而不是只带 pitch deck。第二类是 DRI，也就是对某个具体结果直接负责的人，他不是传统 manager，而是对明确结果负责的人。第三类则是 founder 型 AI builder，既继续亲自做，又继续 coaching，也通过自己的行为给团队示范 AI 能把能力放大到什么程度。她说，如果你是创始人，就必须自己站在前面，而不是把 AI 战略外包给别人。

这套结构会让公司用更小的团队做出极大结果。她特别提了一个新的思维转变：未来真正要最大化的不是 headcount，而是 token usage。她说，最强的公司会是那些“token maxing”的公司。因为一个人加上 AI 工具，可能已经能替代过去一整支很贵的工程、设计、HR、行政团队。所以公司应该愿意接受一个看起来很高的 API 账单，因为它替代的是更庞大、更昂贵的人力成本。

视频最后她对早期创始人给了一个很明确的建议：不要把这件事当成别人会替你判断的趋势，你必须亲自坐下来和 coding agents 共处足够久，直到它们不断打破你原有的能力边界判断。她认为早期创业者在这件事上拥有巨大优势，因为你没有历史包袱，没有几十套旧系统，没有成千上万人需要重新教育。你完全可以从第一天起就按 AI native 的方式来设计系统、工作流和文化。

她还补了一句：对大公司来说，这件事会难得多。因为它们一边要维护现有产品和现有业务，一边还得拆掉多年形成的标准流程和关于“软件应该怎么被构建”的默认假设。有些公司可以靠内部 skunkworks 团队来从零做新系统，比如 Mutiny；但对大多数成熟公司来说，每次改核心流程都可能把原本还能工作的东西弄坏。也正因为这样，创业公司反而更容易在这一波里抢到真正的先发优势。
