节目开头先剪出几段 Anders Hejlsberg 的判断。主持人问 Turbo Pascal 为什么叫 Turbo Pascal，Anders 回答说，因为它快。那是 Audi quattro 和 turbo 很流行的年代，turbo 就意味着快，而 Turbo Pascal 的确快，而且非常互动。

谈到 C# 的设计目标时，他说，团队知道自己想要构建一门面向对象语言，想要 managed code 或 bytecode，从而能面向不同 runtime；想要 garbage collection、exception handling，也想要统一对象系统。谈到 TypeScript 为什么这么流行，他说，很大原因是 tooling。给 JavaScript 加上一个可擦除类型系统，再用它提供优秀工具，生产力提升正是在这里实现的。

主持人介绍 Anders 是技术行业仍在世的传奇人物之一。他创造了 Turbo Pascal、Delphi、C# 和 TypeScript，对编程语言和开发者工具的影响巨大。这次访谈会聊到，如果不是 Sun 和 Microsoft 围绕 Java 的诉讼，C# 也许不会诞生；TypeScript 背后的故事；为什么在当时的 Microsoft 内部开源 TypeScript 是一件大事；以及他从四十年语言设计里学到的东西。

## 从丹麦高中机房到第一个 Pascal 编译器

Anders 说，他最早接触编程，是因为自己在哥本哈根读高中时，学校很早就给学生提供了电脑访问。那是 1970 年代中后期，一台 HP 2100，只有 32K ferrite core memory。机器可以打开看到磁芯，bootloader 在纸带上，因为机器没有 ROM。启动时机器什么都不知道，人要先键入一段指令，让它去读纸带上的 bootloader，再从 14 英寸、1MB 的硬盘上加载系统。

那台机器有 Fortran，有很慢的 BASIC interpreter，也有 HP 自己的 Algol。这个 Algol 编译器有一个奇怪限制：不支持递归。因为机器的 call instruction 会把返回地址存到 subroutine 的第一个 word 里，再跳过去执行。调用自己时，这个返回地址会被覆盖，于是程序就回不来了。没有调试器，人只能非常小心选择算法。

但它能编译成 machine code，所以可以写游戏，比如 lunar lander。这种早期机器很简单，几乎没有层次。你可以一直看到底层，几乎直接站在硬件上编程。Anders 觉得这正是早期计算机的美感。

1979 年，他进入丹麦技术大学。那时 8-bit microprocessors 正开始出现，人们会买 kit computer，自己焊接。机器通常不会一次就能用，所以还要调硬件。他买了一台英国 Z80 kit computer，叫 NASCOM，并开始写 assembly。后来他和大学朋友开了哥本哈根第一家可以走进去买电脑的商店，卖 Apple II、VIC-20、Commodore 64、TRS-80 等。

这些机器都有 Microsoft ROM BASIC。BASIC 很慢，但能让人写程序。Anders 总是想要一门更“真实”的语言，类似学校里学的 Algol。朋友告诉他有个新东西叫 Pascal，比 Algol 还简单。Pascal 不难实现，于是 Anders 写了一个能放进 12K ROM 的小编译器，编译 Pascal 子集。用户可以把 Microsoft ROM BASIC 拔掉，插进他们的 ROM，开机后就进入一个能输入和运行 Pascal 程序的小环境。这就是 Turbo Pascal 的早期前身。

后来他写了一个完整的 8-bit CP/M-80 Pascal 实现，并和 Borland 做了 joint venture。Borland 最初也是丹麦公司，他们通过 royalty contract 销售 Anders 的编译器。1983 年，第一版 Turbo Pascal 发布，随后爆火，超过所有人的预期，最终变成 Anders 的全职工作。

## Turbo Pascal 的产品不是编译器，而是完整体验

主持人问，Turbo Pascal 为什么如此受欢迎。Anders 说，它就是比竞争对手好太多：更快、更小、更互动，而且更便宜。当时编译器通常要 500 美元，而且只是编译器。用户还要另找编辑器，还要在不同软盘间切换 compiler pass。Turbo Pascal 让这一切消失，只卖 49.95 美元。这个价格甚至光买手册都值，所以盗版也少一些。当然他们也开过玩笑，说所谓俄罗斯 site license，就是卖给俄罗斯一份，然后它被复制到各地。

Turbo Pascal 从一开始就不是“只做编译器”。Anders 说，他们想做的是一个 experience。你不只是 compile program，还要 edit、run、debug，还要有 runtime library。所有环节都要一起工作。目标是让它像 BASIC interpreter 一样互动，同时拥有编译语言的性能和 Pascal 更好的语义与语法。

早期 Turbo Pascal 没有真正 debugger。调试时常用 `write` 语句。如果程序爆掉，runtime error 会打印程序计数器所在地址。编译器有一个模式：compile but stop at this address。它生成 object code，当输出走到那个地址，就看自己正在解析源代码的哪一段，从而大致定位错误行。没有 line maps、没有调试器，只是利用编译器足够简单，能在某个 object output 地址停下来。

这种“语言加 IDE 加 runtime 的整体循环”后来也延续到 Delphi。Delphi 的背景是图形用户界面兴起，大家从 DOS 文本模式转到 Windows GUI。Microsoft 已经有 Visual Basic，它很令人印象深刻，但仍有 interpreted、性能和 extensibility 上的问题。Anders 团队原本想做 Visual Basic 竞争者，后来又看到 client-server applications 和数据库连接企业应用的兴起，于是做出一个既像 Visual Basic 那样 rapid application development，又有编译器支持，并面向 enterprise client-server apps 的工具。这就是 Delphi。

Delphi 至今仍有用户。主持人提到，Skype 桌面应用曾经是 Delphi 写的，2012 或 2013 年左右曾计划重写，但中途停下，所以那个客户端可能一直延续到被停用。Anders 说，Delphi 的 VCL，也就是 Visual Component Library，让人能继承组件、放到 palette 上、拖拽到 form designer 里，确实是构建 Windows desktop apps 的非常好方式。

## Sun-Microsoft Java 诉讼如何间接促成 C#

Anders 1996 年加入 Microsoft，最初是做 Java 开发工具，也就是 Visual J++。当时 Java 刚兴起，浏览器和 applets 让行业几乎相信 Java 会把世界扁平化：write once, run anywhere，所有人以后都写 Java。

Visual J++ 1.1 基本像是把 Visual C++ 里的 C++ 编译器拿掉，塞入 Java 编译器，然后称为产品。它不够 interactive，也不够 rapid application development。Anders 带着 Turbo Pascal 和 Delphi 里积累的互动开发工具经验，参与 Visual J++ 6.0。他们还构建了 WFC，类似后来的 WinForms，用 Java 构建 Windows desktop apps。

J++ 技术上进展不错，但 Sun 和 Microsoft 的诉讼改变了路线。Anders 说，这和技术没关系，是商业和法律问题。但结果是，Visual J++ 不可能成为企业愿意下注的平台。没有公司愿意把应用写在一门被法院禁令影响的语言和工具上。Microsoft 也意识到，把开发平台押在竞争对手授权的技术上不是好策略。

与此同时，Microsoft 的开发工具分成两极：Visual Basic 非常易用、适合快速构建应用，但性能和 extensibility 不够；C++ 加 MFC 很强大，但使用复杂。开发者真正想要的是两者结合：C++ 的 power 和 productivity，加 Visual Basic 的易用性；还想要 Java 已经展示出的现代特性，比如 garbage collection、exception handling 和更面向组件的模型。这些因素共同催生了 .NET 和 C#。

.NET 和 C# 是同时推进的。团队知道自己要构建语言无关 runtime，让 Visual Basic、C++ 和其他语言都能运行在上面；同时也需要一门能吸引 Visual Basic 和 C++ 用户、并与 Java 竞争的新语言。

C# 的目标包括：面向对象、managed code/bytecode、可面向不同 runtime、garbage collection、exception handling、统一对象系统，以及让 properties、methods、events 成为第一类概念。C# 里任何东西都可以赋给 `object`；value type 会被 box；对象是 self-describing 的，可以通过 reflection 在 runtime 询问它是什么，并动态操作。这些都是 C# 设计的重要部分。团队还希望把语言交给 standardization committee，给生态一个标准化基础。

## 小团队、长期设计和 Roslyn

主持人问，在 Microsoft 内部构建一门会被数百万开发者使用的语言，需要什么样的团队。Anders 说，早期他们决定由一个小设计组共同设计，而不是一个人拍板。大约六七个人，每周三次，每次两小时，坐在一起从顶层开始讨论。这些人都做过或参与过编程语言，知道什么该做、什么不该做。

Anders 说，语言设计 90% 是相同的，10% 是新的。每门语言仍然需要编译器，编译器大体结构差不多；只是随着时代发展，人们还要求 IDE、frameworks 等。团队每次有新想法，就立刻尝试“射杀”它：这个想法有什么问题？如果它能经受住这类批评，就可能是一个好想法。Anders 同步写 language specification，另一组人用 C++ minus 实现编译器。

最早 C# 编译器并不是 self-hosted。直到后来 Roslyn 项目，编译器才用 C# 自己实现。早期 IDE 还不那么 fancy，syntax colorization 和 statement completion 只是逐渐出现。他们为了 IDE 做了一个 mini language service，同时又有真正的 compiler。随着 generics、LINQ 等特性加入，两个实现并行维护越来越痛苦。每加一个语言特性，real compiler 和 language service 都要各实现一遍。Roslyn 的目标就是用同一个 compiler 既做 command line compiler，又做 IDE 里的 interactive service。

TypeScript 从一开始也采用类似思想。Anders 认为，这里面有很多经验学校并没有教。

## async/await 为什么能被复制

主持人提到 C# 的 async/await 后来影响了 JavaScript、Python、Rust 等语言，问 Anders 他们当时做对了什么。

Anders 从 event loop 讲起。很多环境是 cooperative multitasking：一个事件循环分发事件，你处理事件，然后 yield 回循环。问题是，如果中间有 long-running work，怎样在中途停下来，把控制权还给 event loop，等结果准备好后再回到原处继续执行？

手写这种逻辑要构建 state machine。你必须把 stack 上的状态移到对象里，记住执行到哪里，再用一个大的 case statement 包住整个逻辑。对人来说，这很难写，也很难读。但把 serially executing code 转换成 state machine，也就是 continuation-passing-style translation，是编译器可以机械完成的。只要引入语法标记你想在哪里 yield，这就是 `await`。`await` 的意思是：我在这里让出控制权，等待这个 promise 完成，之后请回到这里继续。编译器会围绕它生成 state machine，把跨越 await 后仍要保留的状态放到 heap allocated 对象里。

这让程序员得到一种错觉：自己仍在写普通顺序代码，痛苦的 callback 和 state machine 转换由编译器负责。JavaScript 曾深受 callback style 困扰，async/await 的价值正是在这里。

Anders 也承认 async/await 有 function coloring 问题：有 async functions 和 regular functions，红函数能调用蓝函数，但蓝函数不能直接调用红函数。只要一个函数要调用 async，上面的调用链也常常要变 async。这不完美。Go 的 goroutines 和 green threads 是另一条路径，用语言级 lightweight threads 避免 function coloring。但对于已有 JavaScript、C# 和 Windows event loop 这样的环境，async/await 是正确解法。

## TypeScript：不是替代 JavaScript，而是修好 JavaScript

谈到 JavaScript 的崛起，Anders 说，早期大家并不认真看 JavaScript。真正让它起来的是几件事汇合：V8 让 JavaScript 执行平台大幅成熟；HTML5 被 ratify，浏览器能构建真实 UI；iPhone 带来设备革命，世界不再只是 Windows PC，但所有设备都有浏览器和 JavaScript。真正跨平台语言不是 Java，而是 JavaScript。

Microsoft 内部触发 TypeScript 想法的事件之一，是 outlook.com 团队来找 C# 团队，希望把一个叫 Script# 的东西产品化。Script# 是一个 cross compiler，可以把 C# 编译成 JavaScript，把 JavaScript 当作 instruction language，在浏览器里跑 C# 应用。Outlook 团队想要它，是因为这样能用 grown-up programming language 和 grown-up tooling，用 Visual Studio、project system、refactoring 等。

Anders 的反应是：也许更好的方式不是让人写另一门语言，而是修好 JavaScript。JavaScript 本身其实是不错的小语言，Brendan Eich 把 first-class functions 做对了，这是很大的优点。它真正缺少的是 type system。而 Anders 他们从经验中知道，没有类型系统就做不出真正好的 tooling。你可以做 decent tooling，但无法在大团队中 scale；无法把 intent 表达进代码，也无法可靠分析，无法在 IDE 中提供 statement completion、refactoring、go to definition、find all references 等。

于是 TypeScript 的想法诞生：做 JavaScript 的 superset，加上类型系统，然后把类型擦除掉。类型系统成为强 tooling 的基础，而运行时仍然是 JavaScript。

TypeScript 必须开源。Anders 说，Microsoft 当时已经意识到开源不会消失，开发者也在用脚投票。但公司 DNA 仍然会把人往相反方向拉。TypeScript 团队非常清楚，如果他们拿一门 Microsoft 专有语言去吸引 JavaScript 社区，绝对没人来。它必须是 open source。最终，Anders 和 Steve Lucco 两位 technical fellows 坚持推动，拿到了开源许可。

不过他们也付了“税”：最初必须放在 Microsoft 自己的开源仓库 CodePlex 上。那里几乎没人。前两年基本很冷清。直到 2014 年迁到 GitHub，TypeScript 的采用才真正开始加速。这也改变了他们的工作流。早期只是 open source，不是 open development：把源代码丢到仓库里，从外部 issue 抄回内部 tracker。迁到 GitHub 后，整个开发流程也转向开放。Anders 认为，这正是 TypeScript 能变好的关键之一。

## TypeScript 为什么最终登顶

主持人提到，2025 年 11 月的 GitHub Octoverse 显示 TypeScript 成为 GitHub 上最流行语言。Anders 说，这不是一夜之间发生的。TypeScript 先出现在第十名，然后多年慢慢爬升。它一直坐在 JavaScript 旁边。如果把 JavaScript 和 TypeScript 加起来，其实早就是第一，只是用户是否写 type annotations 的区别。

越来越多开发者选择类型，原因还是 tooling。TypeScript 的 erasable type system 带来了真正的开发者生产力。VS Code 也是关键 sister project。VS Code 用 TypeScript 写，是 TypeScript 的早期采用者，两个团队长期紧密合作。这种互动也推动了 Language Server Protocol 的发明。今天几乎所有工具厂商都用 LSP 在 IDE 中提供 interactive services。

Anders 解释 TypeScript 编译器 pipeline。典型编译器先有 lexer/scanner，把文本变成 tokens；然后 parser 检查 token 序列，生成 abstract syntax tree。TypeScript 多了一个 binder pass，把 declarations、symbol tables 和 control flow graph 绑定到 AST 上，方便后续查名字。之后是 type checker，这是 pipeline 最大部分，负责语义检查、推断类型、判断类型关系、检查调用是否存在。最后是 emitter。TypeScript 早期不仅擦除类型，也做 downleveling，把新 ECMAScript 特性转成旧 runtime 能跑的代码，比如 classes 转成 constructor functions。现在浏览器大多 evergreen，downleveling 没那么重要，emitter 很大程度上就是擦除类型并输出 JavaScript 和 declaration files。

但 TypeScript 编译器真正特殊之处，是它同时是 IDE service。命令行编译器可以从头跑到尾；IDE 里的程序则永远处于破碎状态，因为用户正在打字。用户按下点号时，IDE 要在 200 毫秒内知道 dot 前面的表达式是什么类型，后面能补全什么。项目可能有 50 万行代码，不可能每次全量编译。TypeScript 因此大量使用 laziness、deferred work、functional reuse。没有修改的 499 个文件 AST 可以保留，只重建当前文件；不需要计算所有类型，只从用户当前位置开始解析足够多的信息，回答眼前问题。

Anders 说，这是一种和教科书里传统 compiler 不一样的写法，因为互动性成为核心约束。

## TypeScript 的类型系统为什么适合 AI

谈到 JavaScript 未来，Anders 说 TypeScript 会跟随 ECMAScript committee，在标准特性到 stage 3 或 4 后实现。TypeScript 的 playground 是类型系统。作为个人偏好，他喜欢 functional programming，希望 JavaScript 有更好的 expression form，比如能在表达式里给临时结果起名字的 `let ... in ...` 风格，而不是每次都要跳出 expression context 声明变量。

TypeScript 最特别的地方是 gradual typing：你可以有类型，也可以没有类型。其他语言通常强制所有东西有类型，因为需要用类型生成 machine code。TypeScript 的类型只服务开发体验和检查，运行时全部消失。因此 TypeScript 不必证明 100% 正确。有些 recursive structural types 分析到一定深度后就会进入无穷递归深渊。TypeScript 可以说，已经证明到四层，大概够了。即便只能检查 99%，也比 JavaScript 的 0% 强得多。因为运行时仍然是 JavaScript，行为是动态定义好的，不会生成不确定 machine code。

主持人问，是否需要为 AI agent 修改语言或创造更适合 AI 的语言。Anders 半开玩笑地说，对 AI 最适合的语言，就是训练数据里最多的语言。这也是 AI 擅长 JavaScript、TypeScript 和 Python 的原因。但他也认为，AI 选择 TypeScript 而不只是 JavaScript，很大程度是因为类型帮助它生成更好程序。TypeScript 的组合恰好合适：没有上下文的地方写类型，有上下文的地方推断类型。如果强迫 AI 每个地方都写类型，它反而更容易出错，也会重复太多 token。Type annotations 标出边界，inference 则保持 DRY，减少 token。

AI 生成代码越来越多后，Anders 认为一些语言特性会更重要。第一是 types 和 inference。第二是 locality。不要有一堆全局状态，让 AI 必须理解整个 program 才知道发生了什么。C/C++ 的 include files、PHP 早期 globals、早期 JavaScript 全局 monkey patch，都会让上下文窗口和理解成本变大。好的 locality 意味着一个 source file 清楚声明 import/export，能从单个文件提取它和外部世界的协议，而不必理解整个代码库。

他还认为，language services 和 semantic search 会越来越重要。Agent 今天常用 grep 或 ripgrep 找引用，但这不是语义搜索。如果属性名叫 `address`，全文搜索会找到大量无关 address。LSP 已经提供 find references、go to definition 等语义能力，但它们可能需要变得更适合 AI 使用。AI 喜欢 command line tools，而 LSP 通常不是命令行接口。未来也许会有保持项目 hot 的 server，给 agent 提供快速 semantic questions，十分钟不用就释放。

## AI 后，程序员更像项目经理，但不能放弃理解

Anders 说，TypeScript 团队已经在使用 AI。比如 GitHub 上用 AI review pull requests；用 AI 修简单 issue；TypeScript 正在把编译器迁到 native code，团队要把过去一年半旧代码之后的 PR 搬到新编译器上，AI 在这方面有帮助；还会让 AI 写测试。没人喜欢写测试，AI 很喜欢写，可以生成大量同风格测试。

但他很明确地说，AI 并不能让团队免于理解自己在做什么。尤其编译器和语言处在很底层，类型、符号、binding、parsing、数据结构、性能之间关系复杂。AI 对表层工作有用，但到大图景和深层结构时，还不到那个水平。

他还提醒，AI 和编程语言之间有一个根本关系：没有编程语言，AI 很难到达确定性。AI 本质上 stochastic、不确定，同一个问题下次可能回答不同；但应用程序不能这样，银行 app 不能 hallucinate。最终总需要某处“rubber meets the road”，用可推理、可复现的程序把行为固定下来。所以在数据问题上，与其问 AI 答案，不如让它写一个计算答案的程序。

主持人问，AI agent 成为日常工具后，软件工程 craft 哪些部分会变不重要，哪些会更重要。Anders 说，某种意义上我们都会变成项目经理。我们有一群叫 agents 的 junior programmers，它们会吐出大量代码。但必须有人看大局，review 这些代码，构建架构，监督工作。Craft 会从写代码转向 review code、design architecture 和 oversee work。

Anders 承认，这会改变乐趣。对他来说，写代码、看它跑起来，一直是最有满足感的部分。AI 某种程度上夺走了这一点，因为他对 review code 没那么感兴趣。但 review process 也可以被重新设计得更有趣。今天的 diff 按字母顺序列出来，让人自己理解变化；未来可以有 AI commentary，引导 reviewer 理解改动、解释顺序和意义。

他认为，认为 AI 会直接消灭程序员是愚蠢的。Vibe coding 很好，只要它有效；一旦偏航，而你不知道发生了什么，也说服不了 AI 修好，就会陷入困境。人不能放弃理解。程序责任也不在 AI 身上，而在程序员身上。你不能回头对 AI 说“我要解雇你”，那没有意义。AI 是让程序员更高产的工具，但确实会改变我们写程序的方式。凡是 AI 可以快一百倍输入的东西，人就没必要继续手敲。

## 开发者真正关心的是进入状态

主持人问 Anders，从三门广泛使用的语言中，他学到开发者真正关心什么。Anders 说，开发者关心的是 productive，关心能不能进入 zone：工具像手指延伸一样，在恰当时刻回答你、支持你，让你感觉一切在点击。

因此，语言设计不能只看语言。要看整个 experience。程序员会把工作生命中大量时间花在这个体验里，所以他们会对工具和语言产生近乎宗教式的依恋。Turbo Pascal、Delphi、C#、TypeScript 共同体现了这一点：编译器不是产品，整个 edit、compile、run、debug 循环才是产品。IDE 和语言不能完全分开。

谈到性能，Anders 说这取决于应用类别。像他们做的编译器、工具、推理服务、金融高频交易等，性能绝对关键。TypeScript 团队花一年半迁到 native code，就是因为用户关心工具性能。但也有很多地方，性能差 10 倍用户都感知不到，就不值得优化。

他的个人开发环境仍然是 Windows，一台 Lenovo P1 笔记本，OLED 屏幕和好键盘。工具是 VS Code 和 GitHub，AI 编程辅助也主要在 GitHub 和 VS Code 工作流里。他说，在实现 TypeScript 编译器和语言特性时，LLM 目前帮助有限，因为这是一个大型 brownfield codebase，而且训练集里编译器代码本来就没有那么多。相比之下，React GUI app 太多了，AI 擅长也不奇怪。

## 编程语言是十年周期的长游戏

Anders 已经在 Microsoft 近三十年，做编程语言四十年。主持人问他为什么长期留在同一个领域。Anders 说，developer tools 和 programming languages 就是他热爱的东西。它们是复杂的 algorithmic problems，而且依赖相对少，你更像是在自己从底层构建，而不是坐在别人 framework 上抱怨。

语言也是长游戏。他说，自己做的东西往往至少是十年周期。Version 1 很好，但一定有问题；Version 2 修很多东西；到 Version 3 才真正变好；然后还要说服人采用。TypeScript 和 C# 都是这样。Microsoft 作为一家 fundamentally developer-focused company，也给了他罕见机会：让一家大公司把力量押在你创造的编程语言上。

最后他推荐 Niklaus Wirth 的《Programs + Data Structures = Algorithms》。这是他学习 hash tables、小编译器等基础知识时的启蒙书。它符号不重，例子丰富，很适合工程师。他认为，尤其在编程语言领域，很多基本东西并没有变。

主持人最后总结说，Anders 提醒人的一个关键点是：语言设计是十年周期，不是季度和 sprint；优秀技术工作常来自经验丰富的小团队，而不是大型委员会；IDE 和语言要一起看，因为真正产品是客户完整使用方式，而不是你负责的某个局部。
