节目开头先剪出 Max Shing 的几段判断。他说，过去人们很容易把做不到某件事归结为技能问题，但当 AI 把很多技能放到手边之后，真正重要的反而是 agency。Agency 在世界上并不平均分布。如果一个人想培养这种能力，他会提醒自己：“能不能像偷来的一样开 Notion？”也就是不要把自己只当作岗位说明书里的角色，而要真的推动变化。

他还说，某一天你会醒来意识到，世界是由并不比你聪明的人造出来的。这个认识会让人突然明白，很多东西其实可以改变。AI 让每个项目的前 10% 几乎免费，构建一个创业项目的第一版几乎不需要成本。与此同时，taste 会变得更常被讨论。Max 对 taste 的定义是，你能在脑子里运行一个虚拟机：给定一个想法，你能预测某个特定人群会不会喜欢它。这需要大量 reps，就像训练模型一样。

主持人 Lenny 介绍说，Max 很难用一个标签描述。他曾在 Google 做产品经理，在 Heroku 领导设计团队，在 Nat Friedman 领导下的 GitHub 同时做设计和工程，也创过两次业，现在是 Notion 的产品负责人。主持人认为，大家现在都在谈角色融合，设计师、PM、工程师之间的边界正在坍缩，而 Max 很早就已经是这种混合型人才，所以特别适合讨论 AI 之后产品团队会怎样变化。

## 为什么 Notion 让设计师和 PM 进入代码

Max 先讲了 Notion 内部变化的起点。他加入 Notion 时，团队正在做很多聊天界面，设计师还在 Figma 里画这些界面。他想起 Bret Victor 的演讲《Stop Drawing Dead Fish》：静态图片无法真正表达一个会动的系统。聊天界面尤其如此，必须“感受”AI，而不是只看一个静态 mock。

于是，Max 和两位设计师搭了一个非常简陋的 playground。它是一个小代码库，对 LLM 很友好，使用模型擅长处理的工具。团队把聊天界面的 prototyping 挪到这个 playground 里，而不是一开始就进入庞大的 Notion 主代码库。Notion 主代码库经过十年演化，模式很多，不一定对 agent 友好。playground 的目标是尽可能不吓人、尽可能 one-shotable，让人先克服对 terminal 的恐惧，然后把构建体验变成类似聊天。

这个 playground 最初只是为了让人上跑步机。随着模型能力提升，同一批设计师和 PM 已经开始在一定程度上直接贡献生产代码。Max 不想把这说成自己一个人的功劳，他认为这本来也会发生，但这个原点很重要：让设计师在真实媒介里思考，而不是只用静态图描述动态系统。

主持人问，现在设计师和 PM 到底应该多大程度 ship code。Max 说，他并不关心设计师写的代码是否最终进入生产。真正重要的是，代码迫使他们面对媒介本身。假如一个设计师只会用 Codex 或 Claude Code 调整 UI 小细节，但不理解 agent loop；另一个设计师不擅长传统编码，却深刻理解 agent loop 应该怎样工作，Max 更想要后者。因为要理解 agent loop，只能在它实际构成的材料里设计，而当前这种材料主要就是代码。

所以，他不是为了让设计师变成交付链条上的齿轮，而是希望他们成为材料的主人。设计师写代码的意义，不在于多交付几个 feature，而在于他们必须理解自己正在设计的系统如何运作。

## Agency 会变成真正的分水岭

主持人问，AI 之后哪些人会适应得最好。Max 说，最关键的仍然是过去就存在的东西：agency。以前很多人可以说“我不会做这个，因为我没有某项技能”。现在模型把很多技能补齐后，剩下的问题是，你是否真的相信世界可以被改变，是否愿意主动改变自己的角色。

他觉得那些总是在追问“PM 的工作边界是什么、设计师应该做什么、工程师的职责是什么”的人会更难。相反，有 agency 的人会把角色改造成自己认为应该存在的样子。

Max 举了 Notion 内部两个例子。Brian Leven 本来就模糊了工程和设计的边界，但他还会超出日常职责，主动去做招聘，思考组织需要什么人，然后出去找到这些人。Max 用一句话描述这种状态：drive Notion like it's stolen。即使你不是创始人，即使你加入时公司已经有很强的 product-market fit，你仍然可以像拥有它一样推动变化。

另一个例子是 Eric Lou。他过去写很多 strategy docs，后来问 Max：如果未来你创业，会不会雇我？Max 说，前 10 个人里不会，因为他不需要一个纯产品经理。Eric 于是决定补齐技能，先花更多时间在 Figma 里，而后又进一步跳过 Figma，直接构建 prototype，把自己的想法做出来给别人看。这就是 agency：不是接受角色定义，而是主动改变角色。

主持人追问怎样培养 agency。Max 说，他最在意的是 Steve Jobs 那句话：有一天你会意识到，世界是由并不比你聪明的人造出来的。很多人是自己意识到这一点，也有人很早遇到好老师。Max 看到的共通路径是 making。只要不断 tinkering、不断做东西，人就会进入一个创造的循环：做一把椅子、改一顿饭、搭一个工具，都能让你感到世界不是固定的。Agency 不是绕过老板、争取权限，而是先从做东西开始。做得多了，别人会注意到，你也会越来越相信自己可以改变东西。

## Malleable software：软件应该更接近使用者的利益

Max 接着解释 malleable software。他把它定义为：软件应该更接近使用者的利益，而不是只服从制造它的公司的利益。他说，人们不会接受一个不能重新摆放家具的客厅，也不会接受厨房布局永远由别人决定。但今天很多软件就是这样：app 是一个小方块，界面、数据归属和行为都粘在一起。你喜欢这个 app，但想改一点行为时，通常做不到。

另一端是完全自己维护 Linux 发行版。它高度可塑，但代价是你要从底层开始处理一切，甚至可能被 trackpad 为什么不能用困住。Max 关心的是：人是否拥有自己的 computing life。现在很多人因为 AI 开始为播客录制、节目准备等场景做自己的小工具，突然意识到“我可以自己造工具”。这是一种 malleable software。但如果每个人都只是单独造一个小工具，它还不够。Max 更关心的是怎样在平台或操作系统层面鼓励这种可塑性，同时保留实时协作、安全和团队工具的能力。

他提到 Ink & Switch 以及 Jeffrey Lit，他们长期思考怎样让软件更可塑，让人更有所有权，而不是回到缺乏协作和安全能力的旧时代。

主持人把这个想法和 Dieter Rams 批评博物馆里设计椅子的片段联系起来。Max 说，他喜欢那个片段，一方面是因为德语里那种不满意地用手杖指着东西说“这个不够好”的方式很好笑，另一方面也因为他相信设计首先应该有用，然后才是漂亮。很多被放进博物馆的椅子也许看起来像艺术品，但你真的坐上去就会发现它们并不好用。

这也连接到建筑如何学习的观点。一个最适合你的家，很可能不是建筑师一次性设计出来的，而是经过长期使用、调整和改造，慢慢适配你生活方式的结果。房子改墙成本很高，软件本应更低成本地可塑。

## SaaS 不会消失，但会回到更通用的工具

主持人问，既然软件变得可塑，SaaS 会不会被个人用 AI 自建工具取代。Max 认为“SaaS apocalypse”被夸大了。2010 年代很多 SaaS 的确像一个围绕 spreadsheet 做出来的高级表单，它比 spreadsheet 更不灵活，但价值在于引导用户按正确方向填写信息。AI 会改变这类软件，但 as a service 这部分仍然重要。

大多数人不想维护完整软件栈。Max 自己也曾在周末试着重建一个给自己用的 Notion，只是为了探索一些让他不满意的边界。但他不认为普通人真的想长期维护这类工具。软件像花园，需要照料。人们为 as a service 付费，买的是维护、专家对问题的长期思考、可靠性和持续演进。

他猜测，软件会更像 1990 年代的一些通用工具：word processor、spreadsheet、FileMaker Pro 这类东西会回来，但仍然会以 service 形式存在。同时，安全等领域仍然需要专门工具，因为那里有人愿意为特定用户问题走到最后一公里。

Notion 在 Max 看来并不是传统意义上非常窄的 SaaS，而更像一个相对可塑的 general tool。AI 又降低了入门门槛。有人说，因为 Notion AI，自己终于理解并开始使用 Notion。Max 觉得这正说明，AI 可以变成 tutor，让更多人进入一个原本有些难上手的通用工具。

## 每个项目的前 10% 已经免费

主持人问，Max 的工作和几年前相比最大的变化是什么。Max 说，最明显的是每个项目的前 10% 现在几乎免费。很多时候，已经没必要先写 PRD；可以先做一个粗糙版本，让别人看到你想构建什么。甚至可以说，第一版创业产品的成本几乎降到零。

如果慷慨一点，也可以说前 90% 变得容易了，但最后 10% 仍然是另一个 90%。真正难的是把东西打磨到可靠、有质量、可长期使用。AI 让探索路径更便宜，你可以派 10 个 agent 分别探索 10 个方向，再回来判断自己是否正确。这和 GitHub 过去常说的“demos, not memos”一致。以前可以让人写 changelog 或 blog post 来表达用户会看到什么；现在更可以直接给出产品版本，让大家反应。

Max 不确定下一步会怎样。他相信 plain text、Markdown 和 code 都非常持久，表达思想为代码也很有价值。但他也怀疑未来是否真的只是反复聊天。Figma 的未来就是一个好例子：有些 Notion 设计师似乎减少了 Figma 使用，有些则继续认为 AI 工具很好，Figma 也很好。直接操作会不会消失？如果 agent 代替人做 direct manipulation，人是否还需要画布？

他觉得速度会改变交互方式。如果推理很慢，人会排队发很多任务，然后去走一圈，回来 review。如果推理几乎即时，人也许又会回到某种直接操作：像捏 clay 一样，实时塑造代码。到某个智能水平之后，也许很多任务不再需要更聪明的模型，而是需要更快、更便宜、本地运行和更好的模态。他用 Retina display 类比：当你已经看不到像素，就不再需要像素更小。

Max 对“绝对智能”不太感兴趣。他认为社会很多问题并不被 intelligence 限制。对于大量 knowledge work，模型达到 good enough 后，速度、成本、本地化和体验会变得更重要。他更感兴趣的是 exoskeleton，也就是增强人的外骨骼，而不是一个远在数据中心里的神。

## Token spending 不是值得炫耀的指标

主持人问 Notion 对 token spend 的政策。Max 不确定具体政策，但感觉现在更接近 unlimited。他认为在新东西出现时，过早优化成本是错的，应该让人探索。他也猜测，6 到 12 个月后，很多公司会开始严肃追问 ROI，那会让一些人不舒服。

但他不喜欢把 token spend 变成炫耀指标。那就像炫耀一天写了多少行代码。真正的问题不是花了多少 token，而是做出了什么。Meta 曾因为 AI 使用排行榜被批评，Max 反而能理解这种做法：在数万人组织里，要让人跳出原有工作习惯，识别自己工作的 outer loop，给 agent 建一个 software factory，需要大量推动。排行榜也许只是让人开始尝试的一种方式。

他观察到，不同角色进入 AI 的摩擦不同。离工程更远的角色，反而不用太多说服，因为前后能力差距太大，他们会感觉自己获得了超能力。然后公司要提醒他们：这很好，但你也要理解为什么这个 PR 不能合并。工程师这边，Max 引用 Simon Willison 的观点：在写代码阶段，任何人工干预都应该让人觉得像一个 bug。这不包括 code review，他仍然认为人应该投入更多精力 review，但在写作环节，如果人老是要手动插手，说明 verifiability loop 和 software factory 还没有建好。

## AI 改变其他岗位，可能是通过软件继续吃掉世界

主持人问，软件工程已经被 AI 改得很彻底，下一类被改变的岗位会是什么。Max 给出一个 hot take：模型在 coding 上以非常明显的速度进步，但他对其他领域的进展没有同样深的印象。他并不觉得模型在写作等领域有同等幅度提升，自己仍然不喜欢读 AI slop。

但 software is eating the world。如果创建软件、把业务实践编码成普通软件的成本持续趋近于零，世界上就会有更多软件。HR 等非工程团队可以自己自动化很多事情，不再总是打扰工程团队。很多所谓“模型在非代码领域进步”的例子，在 Max 看来其实是把 coding principles 应用到了那个领域。因此，他认为变化不是某个岗位被单独替换，而是软件工程能力流入所有其他领域，软件吃掉世界的速度继续加快。

主持人提到 Codex 产品负责人也有类似观点：最终胜出的 agent 都会是 coding agent，因为它会为自己构建需要的工具。Max 同意。现在各种 agent harness，不管开源还是模型公司自己的，都越来越像 coding agent。

谈到模型生态和 ROI，Max 说，如果 frontier lab 和开放模型之间的差距扩大，权力会更集中，那是他不喜欢的世界。但如果差距没有扩大，企业会更习惯运行自己的模型、微调自己的模型，在很多 good enough 任务上移除 lab 的利润层。那时 ROI 会变成：这个任务交给更小、更便宜的模型是否足够。

他认为现在美国至少有几个有竞争力的 lab 互相追赶，这是幸运局面。如果竞争停止，他会担心。长期看，这可能像云计算战争：某些层会商品化，企业不想被单一供应商锁死。Max 用 Heroku 和 Kubernetes 类比：Heroku 的用户体验更好，但 Kubernetes 更成功，因为它不是替代你的 ops 团队，而是让 ops 团队变成超级英雄，并且不给云厂商锁死你。

## Notion AI 为什么适合 agent

主持人提到，很多人最近夸 Notion AI agent 很有用。Max 说，他自己仍然每天都在想它哪里还不够好，但也承认它好得让他惊讶。Notion 很早就在 AI 上投入，甚至第一版 Notion assistant 早于 ChatGPT，这背后是 Ivan 和 Simon 对 AI 会改变很多事的直觉。

Max 认为，Notion AI 做得好的原因之一，是 agent 需要 context。Agent 不喜欢通过很窄的接口去另一个数据仓库里摸索。Notion 作为 connected workspace，把公司的许多信息放在一起，人们第一次直观理解为什么这种连接有价值：agent 可以在里面 roam around，做事、查资料、遵守权限。

这也和 malleable software 相连。Max 更把 Notion 看成一种 operating system。它和 coding agent 所处的 Unix 环境有相似之处：一个可组合、可搜索、可操作的工作空间。Notion 的 enterprise search、自动权限处理等也为 agent 提供了基础。

主持人把这和开头的“for such a time as this”联系起来：Notion 恰好在 AI 需要大量公司 context 的时候，已经积累了这些上下文。Max 也说，这和 malleable software 一样，不是新概念突然出现，而是过去一直存在，只是原来太难。AI 让它突然变得可用。

## 更快 shipping 与“obviously good”

主持人问，Notion 怎样更快 ship，同时保证东西值得骄傲。Max 说，这非常依赖公司文化。他在 GitHub 和 Notion 都见过类似情况：第一幕已经有极强 product-market fit，随后组织会进入身份危机，纠结下一幕是什么。解决方式往往是提醒大家：你可以直接做事，不必过度 precious。用户当然会因为一些变化不满，但如果公司不创新，他们也会不满。

Notion 内部常说 shots on goal。AI 让实验变便宜，就能增加射门次数。但 Max 也提醒，feature count 和 lines of code、token consumed 一样，是很蠢的指标。他宁愿要更少但真的很好的 feature，并且这些 feature 的组合能力足够强。

他对软件质量仍然不满。他不觉得模型公司也能免于这个问题。CLI 工具很好用，但经常每两周又出现一个刚修过的 regression，TUI 帧率也不理想。Max 想找回一种 Apple 式、机加工一体成型铝块那样的工程质量。

Notion 有一个贴纸叫“let's just only make obviously good stuff”。这句话让人烦，因为它没法完全定义，只能说“看到就知道”。Max 认为第一代 iPhone、ChatGPT 刚出现时，大家都能感到它 obviously good。但这并不意味着团队要躲进洞里直到完美。Max 的另一个核心价值是 incremental correctness：非常擅长迭代。可以先让多个想法生长出来，观察它们如何工作，然后再回头做艰难的整合，把同一类想法合并回一个简单核心。

他举 Notion 自己的例子：客户经常吐槽 Notion 有六种 automation primitives，包括 agents 在内。Max 认同这个问题，但也认为这来自让不同想法先成长。接下来真正困难的是坐下来，把这些分支整合回一个 naked robotic core。

## Taste 来自反复练习和反馈

主持人问，AI 时代大家都说 taste 重要，怎样培养 taste。Max 先说自己不确定自己是否有 great taste，但他看到 taste 的共同来源是带反馈的迭代。Taste 需要在一个具体领域里长期积累，然后才可能迁移到其他领域。

他把 taste 定义为：你能在脑中运行一个虚拟机，给定一个想法，你能预测某个 in-group 会不会喜欢它。没有必要让 80 亿人都喜欢，你要先决定自己服务的群体是谁，然后提高自己模拟他们反应的能力。做到这一点只能靠 reps，就像训练模型：输入一个想法，观察人们反应，再调整。

对软件设计师来说，Max 发现 taste 高的人通常有 side projects，自己负责完整端到端结果；同时也总在试新 app，经常提出“我们要不要试试这个工具”。这有时很烦，但说明他们大量暴露在别人的想法里。另一个重要因素是，让自己周围充满有品味的东西。Notion 的会议室以第一台打字机、Macintosh、Porsche 911 等著名对象命名。坐在这些房间里，会提醒人：自己做的东西还没有达到那个水平。

## 伟大产品通常有一个很小但极强的核心

主持人问，Max 参与过很多成功产品，最终什么最重要。Max 先纠正说，他是“贡献”过这些产品，而不是独自“构建”它们。职业越往后，他越觉得团队是唯一真正重要的东西。单说最佳设计必胜或最佳工程必胜都不对。

他最明确的判断是，伟大产品都有一个很小但极强的核心。最危险的陷阱是相信“再加一个功能，它就终于会很好”。真正伟大的产品不是靠功能堆出来，而是有一个 tiny core 超级强。iPhone 的 multi-touch、GitHub 的 pull request、Notion 的 blocks 和 slash commands、Figma 的实时协作与设计工具结合、Heroku 的 `git push heroku master`、Dropbox 菜单栏图标和稳定同步，都是这种核心。一旦这个核心对了，其他东西才有意义。

他回忆自己 2014 年创办过一个类似文档协作工具的公司，后来 Notion 从网站构建 pivot 到文档协作，投资方因为冲突退出。他们花了大量时间打磨编辑体验，做了 markdown folding 和很多后来 Obsidian 也有的功能。但 Notion 第一版编辑器其实很糟，都是 block，甚至不能跨 block 选择。结果 Notion 还是赢了，因为它的核心方向对了。他们则是在错误的核心上勤奋太久，然后不断加功能问“现在好了吗”，这是一条死亡螺旋。

Max 说，核心好不好通常能感觉出来，但还需要反复迭代让用户真的理解并产生反应。不要因为第一批用户研究失败就放弃核心想法，但也不能以为多加功能能补救一个不对的核心。

## Jobs to be done、UBI 和工作的意义

谈到 jobs to be done，Max 说自己未必会严格认同 Clayton Christensen 的全部理论。他使用这个框架，主要是提醒团队诚实地看用户到底想“雇用”你的产品做什么，而不是你希望用户想要什么。大型组织里，人们 review 自己产品时很容易不再以用户视角看体验，而是以员工视角看“我做了一个东西”。Jobs to be done 能把人拉回来：如果你就是用户，你会买这个东西吗？

他举一个近期 landing page 的例子。团队在描述新功能时，写作能力突然下降，开始用聪明但空洞的 marketing speak。Max 会让他们想象自己站在白板前，真正要向朋友解释这个产品时会画什么、说什么。然后再回头看设计稿：这两件事是同一件事吗？

主持人最后问 Max 关于 universal basic income 的 hot take。Max 半开玩笑半认真地说，我们已经有 UBI 了，它叫 knowledge work。他不把自己的工作排除在外。如果仔细想人类生活和满足真正需要什么，其实没有那么多。我们构建出一层层职位和流程，然后说这些都绝对必要。即使 AI 变强，人类也会发明新的理由，把自己放进和 agent 的协作回路里。

如果有一天 AGI 出现，不必工作了，Max 说自己大概还会做同样的事，只是少开会、少管理。他编码不只是因为有用，也因为那是智力挑战，像下棋或围棋。即使机器更强，也不代表人类应该停止玩。他会继续 tinkering，继续让周围世界更可塑。

在结尾的 lightning round 里，他推荐了几本书：Charles Petzold 的《Code》，因为很多职业程序员其实并不懂计算机如何工作；Ivan Illich 的《Tools for Conviviality》，因为它讨论能让人发挥创造力和自治的工具；James C. Scott 的《Seeing Like a State》，因为高层管理者很容易创造一种假的 legibility，以为状态报告让自己理解了系统，实际却忽略了地面真实。

他喜欢的产品包括 Ghostty terminal、手机上的 Moshi、开源分体键盘 Corne，以及一把高质量 pocket knife。他喜欢的德语词是 `Tüftler`，接近 tinker，但没有英文里有时带的贬义；还有 `Verbraucher`，也就是 user/consumer，但德语里包含“用掉”的意味，让人想到产品的短暂和浪费。

最后，Max 说听众如果想对他有帮助，可以去城市或人造环境里走一走，仔细观察身边的一切都是由并不比你聪明的人做出来的。大多数东西，只要给你 6 到 9 个月，你都能学会从头做出来。由此你会意识到，自己的 agency 比想象中大得多。
