这次分享从一个很具体的产品故事开始。Every 的联合创始人兼 CEO 讲到，他们刚刚发布了一个叫 Proof 的应用。这个应用不是传统意义上“先由工程师写好，再让用户使用”的产品，而是他自己几乎完全在 Codex 里做出来的。他强调，自己没有真正看过代码，也不是以工程师的方式逐行检查实现，而是把想法、产品判断和迭代要求交给 agent，靠它把产品做出来。

Proof 的定位是一个面向 agent 的文档编辑器。它有点像 Google Docs，但默认协作者不是另一个人，而是 AI agent。用户可以在里面写 markdown 文档，也可以和 agent 一起讨论、修改、整理内容。这个设想背后的判断是：未来很多工作软件的主要使用者不一定仍然是人，agent 会成为第一等用户。既然 agent 会读、写、改、组织文档，那么文档工具本身也应该围绕 agent 的协作方式重新设计。

产品从想法到上线大约用了十天。上线以后反应很猛：一条推文拿到了一千五百多个赞、几十万浏览量，二十四到四十八小时内就有四千多个 Proof 文档被创建。表面上看，这是一个典型的 AI 编程胜利案例：一个非工程师 CEO，靠 Codex 在很短时间里做出产品，发布后还真有人用。

但他马上补上了另一面。发布后的几天并不浪漫。他把电脑一直开着，晚上也放在旁边，让 agent 继续跑；睡觉中间每隔几个小时醒来检查一下。那时候产品在生产环境里有很多问题，他形容早期版本像“一团燃烧的垃圾”。用户进来、创建文档、触发 bug，他就继续让 Codex 修。这个过程不是一次提示词就优雅完成，而是大量反复、碰运气、补洞、再观察。

他真正想讲的不是“以后所有人都会十天做一个应用”，而是软件工程团队的结构会变。他把接下来团队里会越来越重要的两类人叫作 pirate 和 architect。pirate 像海盗，负责冲进未知区域，快速找机会，靠产品直觉和速度把一个东西做出来。architect 像建筑师，负责把已经被证明有价值的东西重新组织成清晰、稳定、可维护的系统。

pirate 的价值在于探索。他不一定是最好的工程师，也不一定理解全部技术细节，但他知道想要什么，知道用户为什么会用，能把一个模糊的产品机会推进到可测试的状态。在 AI 编程工具变强以后，这类人可以直接用 agent 搭出产品，而不是先写规格、排期、等工程资源。Proof 就是这种方式做出来的。

但 pirate 也有很明显的风险。因为他为了速度会不断让 agent 加功能、改行为、补 bug，代码会快速堆出复杂度。短期看，每一次修改都好像能解决局部问题；长期看，整个代码库会变得越来越难理解。模型在一个混乱代码库上继续改，往往会被已有结构牵着走，修一个地方又引出另一个问题。

所以他的建议很直接：当一个 vibe coded 的原型已经证明“这个东西有价值”，但 bug 开始越修越多、系统开始失控时，不要继续让 agent 在原代码库里重构。更好的做法是丢掉那份混乱代码，从零重建。旧代码证明了需求和产品方向，新代码则应该由 architect 按清晰结构重新搭。

他把这个判断讲得很具体：如果你已经有一个用户真正在用、真觉得有价值的东西，但你发现自己反复提示 Codex 修同一个问题，像拉老虎机一样希望下一次会中，那就是该停下来的信号。继续对着原型下注，只会让混乱结构变得更牢固。

architect 的角色因此没有消失，反而更关键。高级工程师的价值不只是写代码速度，而是能理解系统边界、模块关系、长期演化路径。模型很擅长做局部正确的改动，但它不总能形成全局概念，不一定知道什么抽象应该存在，什么状态应该集中，什么复杂度应该被隔离。

他认为，未来软件团队里 pirate 和 architect 都重要。pirate 负责找到“值得做的东西”，architect 负责把它变成可以长期运行的机器。如果只有 architect，团队可能太慢，错过新机会；如果只有 pirate，团队会很快做出东西，也很快被自己制造的复杂度拖住。

最后他回到 Proof 本身。这个产品不仅是一次 AI 编程实验，也代表一个更大的方向：很多生产力软件会被重新做一遍，因为它们过去默认“人是主要操作者”，而未来 agent 会越来越多地读写、整理和执行工作。文档、表格、项目管理、代码库、设计稿，都可能需要为 agent 重新设计接口和协作模型。

他的结论不是工程师不重要，而是工程团队的分工会重新排序。一个好团队需要能冲锋的人，也需要能建结构的人。AI 把“从想法到可运行原型”的成本降下来了，但这不会自动带来好软件。真正的挑战会转到两个地方：能不能找到值得做的问题，以及能不能把快速做出的东西重建成清楚、可靠、可扩展的系统。
