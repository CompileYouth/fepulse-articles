视频最开始先抛出一个很明确的判断：企业的工作，是始终在客户所在的地方可用。过去这个“地方”在不断变化。上世纪 50 年代是银行网点，70 年代是 ATM，90 年代是网站，2010 年代是移动 App，而到了 2020 年代以及之后，新的“地方”会越来越多地变成 API 和一组可连接到未来对话式界面的服务。

在这句判断之后，讲者又提到另一个自己的实践：他把过去五年里所有和自己工作表层有关的材料汇总起来，总量接近 500 万词，把它们做成一个知识库，作为后续很多事情的基础。他还举了一个例子，说自己在开会时，有个系统会提醒他：你现在在这场会议里做的事情，和你绩效评估里反复出现的某个模式完全一致。主持人在这时打断说，在他接触过的各种“second brain”系统里，这套东西是他看过最高层、最完整的一套。

正式进入 demo 后，主持人先请他讲 Mercury 的 MCP。讲者说，Mercury 刚刚发布了这个东西，已经可以在 Claude 的 connector 里直接找到。如果你进入 Claude，再打开 connectors，就能把 Mercury 接进去。他解释说，这个 MCP 的意义是，你可以直接用自然语言对自己的银行账户或公司账户提问，比如“帮我看看最近几个月的开销，哪里能省点钱”。后台做的事情，是通过 API 把回答这个问题所需的数据拉出来，再由 Claude 去组织答案。

他特意强调，MCP 目前是 read-only 版本，这是出于安全考虑。它并不会直接允许用户通过自然语言去改写账户里的关键动作，而是先以查询和解释为主。主持人还专门确认了一次：这是不是他的真实账户。讲者解释说，这里展示的是一个 sandbox account，不是他自己的真实数据，但里面的数据结构和体验都尽可能接近真实场景。

接着他们开始看实际输出。系统把过去几个月的花销整理出来，用表格和结构化信息给出一些支出优化建议。主持人看到每月 500 美元左右的订阅开销，还半开玩笑地说，虽然自己订了很多 AI 产品，但也不太愿意每月花 500 美元。讲者借这个例子继续说明，Mercury MCP 的价值就在于，它让用户能在一个自然语言环境里，更快地看见自己的资金流向，并更容易发现省钱空间。

主持人继续追问：既然 MCP 现在是 read-only，那是不是就不能直接说“帮我取消 Netflix 订阅”这种话？讲者回答说，对，Mercury 的完整 API 本身是读写都可以的，而且和网页端、移动端能做的事情大体一致；但放到 Claude 里的 MCP 版本目前专门限制成 read-only，就是为了让资金安全和账户控制权更清楚地掌握在用户手里。

聊到实际使用情况时，讲者说，他们对用户的反馈有点惊喜。因为 Mercury 本来做的是面向创业者和野心型个体的银行服务，而 MCP 则是这些 builder 把财务数据带进自己工作流的一种新方式。他举了一个自己很喜欢的例子：洛杉矶有一家动画工作室，在把 MCP 接进自己的财务之后，通过自然语言分析，发现了一个原本不知道的税收减免机会。对他来说，这正是 MCP 真正有价值的地方：业务上下文是独特的，只有经营者自己最清楚；但当这些上下文和金融数据结合起来时，就可能得到原本靠手工很难发现的洞察。

他说，团队内部还做了一个“已经帮用户省了多少钱”的记分牌，而这个数字正在不断上升。有些用户已经靠这套东西省下了上千美元。主持人顺着问，那是不是大家最常问的就是“我每个月最大的花销是什么”和“税上还能怎么省”。讲者说，确实如此，但不仅如此。Mercury 的 API 还能把公司账号里的许多身份信息一起暴露出来，比如 EIN、公司地址等等。所以 MCP 不只是一个查账工具，它还可以变成工作流里关于“公司身份”的一个信息源。

讲者举例说，很多场合你都要临时去找 EIN 或其他公司基础信息，而 MCP 的好处就是把这些数据带到你已经在使用的工作环境里。对他来说，最有意思的场景不是某一个具体问题，而是你可以把财务数据带到任何你正在工作的地方，然后围绕它搭建自己的 dashboard 和自己的工作流。

主持人接着抛出一个更尖锐的问题：很多公司都在说“我要让产品支持 agent，要做 MCP”，但在他看来，MCP 其实是很后面的事。那 Mercury 在做这个之前，究竟先做了哪些准备，才让整个东西用起来这么顺。讲者的回答很系统。他先说，Mercury 走的其实是许多银行过去二十年都走过的那条路：先做一个非常好的网站产品，再配一个很好用的移动 App。Mercury 自己相信，他们在网页和移动端上的银行体验已经是市场上最好的之一。而 API 和 MCP 可以被看成 2020 年代的新一层界面。

他的意思是，MCP 并不是凭空出现的，它建立在大量已经打磨好的基础能力之上，比如稳定的存款账户、资金管理、信用卡、权限管理和消费控制等。等这些底层能力已经足够可靠，才有资格把它们进一步抽象成 API，再进一步变成面向 Claude 的 MCP 体验。

在具体实现上，他还谈到一个很现实的问题：很多 MCP 自己体验起来都很麻烦，常常需要去碰一堆文本配置、服务器配置和凭证设置。而他们在做 Mercury MCP 时，刻意把登录体验做得更像正常网页登录：支持 OAuth，一键授权，用同样的密码和多因素认证，连上之后就像网页银行面板一样自然工作。他们想让用户感受到的，不是“我又在接一套技术系统”，而是“我只是把已经熟悉的银行体验带到了新界面里”。

再往后，他们谈到 API 覆盖率和文档问题。讲者说，Mercury 其实很早就有 API，但最近几个月 adoption 明显变快，越来越多用户会主动创建 API token，或者通过客服反馈表达“我想把这些数据带到别的工作流里”。所以他们这段时间做的重点，是一边扩大 API 覆盖，一边确保它在 OAuth、MCP 这些新的入口里同样好用。换句话说，基础不是“先做个 MCP 展示姿势”，而是先把底层能力真的做成别处能用的产品能力。

整段对谈前半部分传达的重点很明确：未来的企业产品不会只停留在一个给人点击的界面上，而会越来越多地变成一组可调用的服务。界面会继续变化，今天是网页和 App，明天可能是 Claude、是 agent、是别的对话式入口；但企业要沉淀下来的，是能够跨这些入口稳定工作的能力层。Mercury 把银行数据和身份数据带进 Claude，本质上就是在做这件事。*** End Patch
