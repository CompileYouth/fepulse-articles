视频一开始就是“模型发布日”口吻。作者说，OpenAI 今天发布的是 GPT-5.5，他们团队 Every 已经内部测试了大约三周。他开门见山地给出总体感受：这是一个很强的模型，他们用它测了 coding、writing、knowledge work 等各种任务，感觉有不少能力都出现了真正的台阶式提升。而在他看来，最醒目的 headline 还是 coding。

他接着拿出一个团队内部使用的 senior engineer benchmark。这个 benchmark 不是考几道算法题，而是给模型一个 vibe-coded、比较乱的真实代码库，让模型按第一性原理重写它，看最后出来的结果是否像高级工程师做出来的东西。他说 GPT-5.5 在这个 benchmark 上拿到了 62.5 分，而真正的人类高级工程师通常可以稳定拿到 80 到 90 分。它当然还没到资深人类工程师的水平，但已经在明显逼近。作为对比，Opus 4.7 一般只能在 30 多分徘徊，差距大约有 30 分。

不过他马上补充了一个关键前提：GPT-5.5 最强的表现，是在“先用 Opus 4.7 写计划，再让 GPT-5.5 执行计划”这种组合里得到的。他说，只要先拿 Opus 4.7 写好一个清晰、严格、像 contract 一样的 plan，再把这个 plan 喂给 GPT-5.5，它就会变成一头“绝对的猛兽”。接下来的整条视频，很多判断都是围绕这件事展开的。

为了说明 benchmark 到底在测什么，他解释说，这个 senior engineer benchmark 用的是一个叫 Proof 的真实 app 代码库。他让模型面对这套 vibe-coded 的代码，从第一性原理出发去做重写，问题不只是“能不能修 bug”，而是“能不能做出一个概念上更清晰、结构更高级、真的像资深工程师重写过的系统”。为了给 benchmark 一个金标准，他还找了两位真正的资深工程师各自重写同一个代码库，用来和模型输出对比。

他强调，这个 benchmark 还远远没有“刷满”。最好的真人工程师依然能稳定打出 80 到 90 分，而目前所有模型里最好的，还是 GPT-5.5。它在有 Opus 4.7 计划的前提下能到 62.5 左右；没有这个前置计划时，大概也能到 40 多分，依旧明显强于 Opus 4.7 本身。即使让 GPT-5.5 自己先给自己写计划，它也能把分数推到 50 多，但还是不如拿 Opus 4.7 先做 planner 这套组合。

他接着解释，GPT-5.5 真正和其他模型拉开差距的地方，在于它更能抓到代码库里那些核心原则或不变量，然后在重写时不那么容易陷进“patch mode”。也就是说，它不是修修补补地堵小洞，而是更敢删文件、更敢从头按新结构来。它有一种“大胆、果断、有执行力”的感觉，能真的把一个大计划从头跑到尾，持续几个小时完成整段工作。当然，他也承认它并不完美，还离真人资深工程师差 30 分左右，但相比其他模型，这已经是一个明显的 step change。

再说回 Opus 4.7，他的评价很有意思：Opus 4.7 特别擅长写计划。它写出来的东西概念清楚、结构漂亮、像 contract 一样，把“好结果是什么”说得很清楚，比如大文件最后要被拆成什么样，应该删掉哪些东西，哪些模块要被保留。这种计划恰恰是 GPT-5.5 非常吃的输入。一旦有了这种计划，GPT-5.5 就会显得异常有攻击性，真正去把它做出来。

相反，Opus 4.7 自己虽然很会写计划，但执行时经常会退缩，容易变成“这个太麻烦了，我先改一点点”的 patching 风格。旧的 GPT-5.4 在这点上也类似，只是执行力稍微好一些。作者认为 GPT-5.5 在高 reasoning 模式下多出来的那一点“冲劲”，正是它和前代模型区别最大的地方。

他还顺带谈了 planner 的写法差异。GPT-5.5 自己写的计划并不差，概念也都抓得到，但更像是“写给人看的好计划”，偏长，也不够 contract-driven；而 Opus 4.7 写的计划则更短、更准、更像规范文档，有很多非常具体的约束条件。作者的结论是，如果你要把 GPT-5.5 用到最好，要么直接配 Opus 4.7 当 planner，要么自己把提示写得极其明确，把验收标准说得像 contract 一样，这样才能真正激发它那种执行大重写的能力。

除了 benchmark，他还讲了团队成员 Naveen 的实际测试。Naveen 是 Every 的 GM，主要负责 Monologue。他用 GPT-5.5 去做一款叫 Dayline 的待办应用，结果发现它能比较完整地做出一个原生 iOS 和 Mac 应用，而且界面还挺漂亮。Naveen 还拿 GPT-5.5 给 Monologue 做真实发布版本，在预发布阶段就烧掉了大约 9 亿 token。他甚至说，这是他现在最喜欢的模型，也是唯一让他赶上某次功能 deadline 的原因。

当然，也不是所有 coding 任务 GPT-5.5 都一定比 Opus 4.7 强。Kieran 做了一个叫 LFG bench 的东西，更像真实产品开发过程，而不是高强度代码重写。这里会涉及前端、设计、产品感觉和不那么严格定义的任务。Kieran 的结论是，GPT-5.5 表现不错，但 Opus 4.7 在某些上限上仍然更高，尤其是设计感更强的任务上。另一位同事 Mike Taylor 也有类似观察：如果你在做更复杂、计划又没那么充分指定的 vibe coding 任务，Opus 4.7 仍然有优势。所以作者最终把建议说得很清楚：GPT-5.5 不是在所有 coding 场景里无脑最强，它更适合那些规划明确、目标清晰、要求大胆执行的任务。

他还补了一个编程语言层面的观察：团队觉得 GPT-5.5 写 TypeScript 和 Swift 都很好，但 Ruby 的味道就没那么对。Kieran 甚至明确说，做 Rails 项目的人可能不会满意它写出来的 Ruby 风格。也就是说，这个模型不仅任务类型上有偏好，语言风格上也有偏好。

讲完 coding，视频转向 writing。作者说，GPT-5.5 的写作没有 Opus 那么有鲜明人格，尤其不如更老的 Opus 4.6 那么“有味道”，但它在 business writing 上特别好。他自己拿它写投资人更新，几乎一枪就打出了一份接近可发送的版本。Every 的写作者 Katie 过去很长时间几乎都在用 Claude 系列写东西，但 GPT-5.5 是她很久以来第一次愿意认真切过去试的 OpenAI 模型。

Katie 和 Mike 都觉得它在模仿写作风格时做得不错，而且不会过度模仿，整体更克制。正因为这种克制，它反而很适合商业写作。这和前面 coding 部分的感受很一致：GPT-5.5 并不是一个到处都显摆能力的模型，但它在“把一整段真实工作做稳”这件事上很有优势。

接着他谈 knowledge work。这里他几乎是把 Codex 桌面应用和 GPT-5.5 一起夸了一遍。他说，OpenAI 在知识工作方面几个月前还相对落后，但现在迭代得非常快。现在在桌面上做 agentic knowledge work，Codex 配 GPT-5.5 已经是他觉得 best-in-class 的体验之一。它快、能力强、能调用电脑上的应用、能上网、能写 dashboard、能做复杂数据分析，而且整体速度非常好。相比之下，Opus 4.7 在不少实战里显得明显慢，他认为这是 OpenAI 目前硬件优势带来的体感差异。

不过他也补了一个保留意见：为了让 GPT-5.5 更容易被人接受、更“顺口”，它在某些地方可能牺牲了一点对细节的敏锐度。也就是说，如果你做的是那种特别依赖尖锐洞察、特别看重判断准确度的知识工作，他仍然会认真考虑让 Opus 4.7 来做。甚至连前面那个 senior engineer benchmark 的评分工作，他都觉得自己更信 Opus 4.7 的眼光，哪怕他平时更愿意把 GPT-5.5 当 daily driver。

最后他的总结很简单：最近新模型发布得太快了，感觉像隔几周就过一次圣诞节，而 GPT-5.5 是一个很值得认真试的模型。它目前是把 frontier model 的能力装进一个相对容易用、对人友好的包装里最成功的尝试之一。以前他自己几乎所有事都用 Claude，现在已经发生了明显变化：手机上他还会用 Claude，但桌面上、需要 agentic 工作的场景里，他基本都在用 Codex。

他最后还专门提了 OpenClaw 这个 harness。他说，如果你本来是 Opus 用户，OpenClaw 这类 harness 现在可能还是和 Opus 配合得更好一点，但 OpenAI 这边也在不断更新，让 GPT-5.5 在这个环境里越来越能打。如果你以前不喜欢 GPT-5.4 在 OpenClaw 里的表现，那他很建议你重新试试 5.5。整条视频的结论也就落在这里：这不是一个“绝对完美”的模型，但它已经足以改变很多人的实际工作流。*** End Patch
